## 1. 探针飞牌结构判定：从赢墩推演到纯条件（用户定调）

### 1.1 问题
探针 Δ 高只表示"位置敏感"，不必然等于"能飞"。早期实现用单套双明手 minimax 比较"对象放防家两侧时庄家方赢墩"：

- 版本1（总墩差）：`_single_suit_decl_tricks` 比两侧总赢墩 → `K567/234 对 A` 两侧都 3 墩判"不飞"，但用户指出 K 在 A 一侧得墩、另一侧被吃，是飞结构——总墩被 5/6/7 冗余中牌补位掩盖
- 版本2（大间张墩差）：只统计 T/J/Q/K 赢墩 → 冗余中牌仍会先行耗掉 A，K 两侧都能后手得分，差值被拉平
- 用户纠正：**不看赢墩，只看结构**。对侧引牌是模拟出牌，仅用于确认"有飞牌结构"；真实出牌是下一墩的事，DDS 结果与模拟完全不同，模拟值不可用于决策

### 1.2 最终判定（纯条件，用户定义）
```
飞牌结构成立 ⇔ 引牌位置的对侧存在一张 G：
  ① G < 被飞对象 obj（比对象小）
  ② G > 防守方除 obj 外该花色的最大牌（能盖住防家所有非对象牌）
```
`_probe_finesse_ok(state, suit, info)` 纯条件实现；`_single_suit_decl_tricks` 整体删除。

### 1.3 回归测试
`tests/test_probe_finesse.py`（8 用例）：
- 真飞：AQ2/43 伙伴引4/3（K）、K567/234 明手引2（对A）、Qx对AJx 本侧引Q（K）、AKJT98/32 缺Q 伙伴引3
- 不飞：AQ2/43 本侧引2/引A、AJ 对 K 无 Q 间张

## 2. 窗口期启动流程重构（用户定序）

### 2.1 演进背景
- 此前结构池压成"Δ 最大单条"，榜首一致的花色被丢弃 → 误选红桃4（做成 57%）而非引擎榜首草花（75.8%）
- 过手逻辑（含写 flow）嵌在启动中途；过手写在 flow 后若过手牌被将吃拦截，会留下死流程
- 用户定调完整顺序（BM2000 Level 2 A-300 验证通过）

### 2.2 定序（`_probe_lead_finesse_prefer`）
```
过手预检（前置）：伙伴侧条目先求安全过手牌
    ├─ 失败 → 该花色出局（[过手预检]日志）
    └─ 成功 → 条目挂 info["过手牌"] 作代表
7.1 引擎一致：榜首花色 ∈ 候选池 → 尊重引擎（不飞）
7.2 结构排序：代表牌（本侧=探针引牌 / 伙伴侧=真实过手牌）
    候选决策值为主（按 0.02 粒度取档量化，同档视为打平）、Δ 平局决胜
    （注：这里"取档"是对做成率的量化容差，与探针的东/西分桶无关）
7.3 必要性：_finesse_launch_worthwhile 逐花色，首过 = 第一名
7.4 执行：
    第一名=本侧   → 探针引牌直出，写 finesse_flow（标记飞牌开始）
    第一名=伙伴侧 → 出预定的过手牌给对侧，不写 flow（不标记开始）
7.9 9张分砸分流（原逻辑保留：应砸出顶张/顶张回手/非顶张直飞小牌）
```

要点：
- 对侧引牌是模拟产物，仅用于确认结构存在；排序价值**不用模拟引牌值**，伙伴侧用真实过手牌在候选中的决策值
- 过手不启动飞牌：`_partner_overhand_action` 不再写 flow；过手后下一墩重新探测、重走完整介入流程（规避过手牌被将吃拦截后的死流程）

### 2.3 多花色结构池 + 引擎一致优先
- 合池保留**全部**通过 `_probe_finesse_ok` 的花色（同花色取 Δ 高者），不再压单条
- 榜首所在花色若在池 → 直接尊重引擎（`if cur_str[0] in finesse_struct: return None`），这就是"引擎一致优先"

### 2.4 过手牌排除探针结构花色
多花色有探针时，过手牌绝不能来自其他探针结果花色（可能破坏其他飞牌结构造成严重后果）。`_cash_reentry` 新增 `excluded_suits`，来源 `full_output["_probe_suits"]`（本侧+伙伴侧全部探针花色，含被废弃者）；找不到安全过手牌 → 该花色出局/尊重引擎。

## 3. 其他
- **探针确认标注**：`_probe_confirm` 映射（侧|花色|引牌 → 是否飞结构），前端逐条显示 `✓飞结构 / ✗未确认`

### 5.2 组合飞探测门（用户定调，确认过程见 §6.1）
- **背景**：双飞（KQ）时"分家 vs 同家"的真实敏感性被单对象位置稀释——本侧 ♥K Δ0.25 / ♥Q Δ0.18 单条均 <0.4，加和 0.43 才显著；单对象判定会整体漏掉双飞结构
- **规则**：花色内无单条达标时，若有 ≥2 个对象，取各对象自身最高 Δ **加和 ≥ 0.4** → 保留**较高的那张牌**（按点值取大），Δ 改写为加和值，标记 `组合飞=True`，其余对象记入 `废弃对象` 废弃
- **执行配套**：
  - `_probe_finesse_ok` 判定时从 enemy（防家除 obj 外最大牌）剔除废弃对象（否则废物被抬高挡住飞张判定）
  - `_finesse_commit_check` 接应威胁计算同样剔除（经 `finesse_struct["废弃对象"]` 与 `state.finesse_flow_extra` 双来源）
  - 启动写 flow 时废弃对象写入 `state.finesse_flow_extra[s]`（`_register_finesse_flow`），接应侧仍可排除；flow 清理时同步清除
  - 前端组合飞 Δ 值**蓝色加粗**显示
- **修复**：保留"较高对象"曾误取 Q（`max(per_obj.keys())` 按字符串 ASCII，"Q">"K"），改为按 `RANK_ORDER` 数值比较 → 正确保留 K

### 5.3 探针判定收敛为一次（bug 根源消除）
- **背景**：`_probe_finesse_ok` 被调两遍——结构池 pool（行为，废弃对象从顶层取→空）与 UI confirm（展示，废弃对象从"全"[0] 取→有值）参数不一致，同一探针可"显示 ✓ 实际判废"，导致"有结构却无飞牌结构"
- **实现**：删除独立 confirm 循环；pool 循环判定一次，结果同时写入 `_probe_confirm`（含 False，废弃也标 ✗）与结构池；`_detect_finesse_struct`/`_probe_partner_finesse_struct` 对 组合飞/废弃对象 从顶层回退到 "全"[0]

### 5.4 探针展示格式迭代（前端）

### 5.5 Bug：`_register_finesse_flow` 无限递归（RecursionError）
- **成因**：批量替换 `state.finesse_flow[s] = obj` → `self._register_finesse_flow(...)` 时，**方法体自己的第一行也被替换成调用自身** → 启动飞牌即无限递归

- **修复**：方法体首行恢复直接赋值；`_dd_play` 异常分支保留诊断打印

## 6. 决策讨论记录（v1.76）

### 6.1 组合飞保留对象与阈值
- 加和阈值 = **0.4**（与单条阈值一致；用户初写 4.0，物理上两对象加和最多 ~2.0 无法达到，经确认改 0.4）
- 保留对象 = **较高的牌（K）**（符合"先飞高对象、窗口下移自然接 Q"的既有原则）

### 6.2 续飞移除方案的六点影响逐条裁定
1. 每墩重新过闸更合理（此时出牌信息更多，不是盲目续飞；检测到需要过手就自然执行）——成立
2. 更多信息下重闸不会比直接续飞差——成立；仅提示 Δ 是采样统计量，两墩间可能波动致"这墩飞下墩不飞"的噪声跳变（体验问题非正确性问题）
3. 接应来源：登记存活到本墩牌出完即可覆盖同墩队友接应，无需跨墩结构——成立（取消时机须定为"墩结束"而非"接应 return 立即"）
4. 组合飞废弃对象随登记同生同灭，重测重建——成立
5. 9砸后流程天然逐墩重探，独立于 flow——无需处理
6. "正在飞"尊重引擎由重测+重闸自然覆盖——成立
- **关键确认**：A. KQ 飞掉一个组合门消失 → 双飞自然退化为单飞（这正是用户想要的行为）；B. `_probe_finesse_ok` 要求 G 在引牌侧对侧，方向已隐含在判定中——不存在"确认 ✓ 但方向错"的场景（该担忧撤销）

### 6.3 顶张方概念废弃（用户强调，勿再引入）
- 飞牌启动/方向/续飞分析一律**不得使用"顶张方/非顶张方（持 A/Q）"概念**；飞牌可行性唯一判据 = `_probe_finesse_ok`，可确认才进候选池

- 已写入项目记忆（project_memory.md）

### 6.4 待实现清单（用户确认后动手）

### 8.2 启动门控简化（用户定调）
- **删判据 C（升级价值）**：`fin_val > top_val`——榜首按 `blended`（make_rate = 做成率×10000+avg）排序，门控 `_val`=「scoring_val」=做成率，**不同口径**；同口径（imp/avg）时 top 恒最大 → 实际不可达（vesion 残留）。删除后稳成线（≥0.95）恒不启动成为明确语义
- **删 A2（盈余）与 B（失败安全）**：`FINESSE_NEC_SLACK`、`FINESSE_SAFE_PCT` 常量及 `slack ≤1.0`、`fin_floor ≥ need` 判据删除；退让说明保留"盈余 +X.0"诊断
- **A1 加飞牌下限**：新增 `FINESSE_NEC_MIN_RATIO = 0.50`——`top_make < 0.50` 且 飞牌/榜首 ≥0.50 才必启动（堵"25% 换 45%"缺口）；不足则落 D 闸裁决
- **D 比值放宽**：`FINESSE_NEC_RATIO` 0.90 → **0.70**（用户调低；0.86 比值案例——♥4 59.1% vs ♣A 68.5% → 恢复可启动）

### 8.3 最终门控形态
```
top_make ≥ 0.95                        → 退让（不飞，尊重引擎）
top_make < 0.50 且 飞牌/榜首 ≥ 0.50    → 必飞（契约必要）
top_make < 0.50 且 飞牌/榜首 < 0.50    → 落 D 闸（≥0.70 才飞，否则退让）
0.50 ≤ top_make < 0.95                 → 飞牌/榜首 ≥ 0.70 → 飞；否则退让
```

### 8.4 行为变化提醒
- 双飞 K/Q：飞掉一个 → 组合门只剩单对象 → 单条 Δ 不达标 → 自然停止（用户要的退化）；后续某侧某墩组合门重新达标（或需要过手再飞）→ 重新探测重新启动
- 稳成（≥95%）局面永不主动启动飞牌（C 删除后的明确语义）
- 登记只存活本墩 → "回手→下一墩引飞"跨墩衔接由重探+重闸完成，若采样波动致 Δ 掉阈值则链条断（用户接受，与"敏感度消失即停止"同源）
