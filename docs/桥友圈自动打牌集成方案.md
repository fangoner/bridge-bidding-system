# 桥友圈自动打牌集成方案（AI 替打）

> 状态：方案讨论稿（v1，未开始写代码）
> 目标：利用本系统的 AI 决策能力（叫牌：DeepSeek + JF 约定检索；打牌：DD/αμ/LLM 引擎），
> 在**桥友圈电脑网页版（练习桌/好友房）**上替用户自动叫牌 + 自动打牌。

---

## 1. 背景与现有资产

### 1.1 需求
- 平台：桥友圈（中国桥牌协会官方在线桥牌平台）**电脑网页版**，用户使用 Edge（Beta）浏览器。
- 范围：叫牌 + 打牌**全自动**替打（单座位）。
- 场景：练习桌/好友房（非正式比赛）。
- 时限：每步时间宽裕（几分钟级），可上深度引擎。

### 1.2 本系统已有的可复用资产（重要！）
| 资产 | 位置 | 说明 |
|---|---|---|
| 桥友圈视觉识别 prompt | `llm/doubao_client.py` | 已有"页面类型: 桥友圈"识别、叫牌表识别要点（"双无/南北有局"等）、单家手牌识别 |
| 截图触发与剪贴板读取 | `utils/screenshot.py`、`api/main.py` | Win+Shift+S 触发 + 剪贴板哈希防重 |
| Edge 窗口定位 | CLI 截图功能 | 已有按标题（"桥友圈 - 个人"）匹配窗口并激活的代码基础 |
| 叫牌决策 | `bridge/bidding_service.py` | BiddingService：关键词提取 → JF 检索 → 主/备 prompt |
| 打牌决策 | `bridge/play_service.py` + `bridge/mcts/` | 7 引擎，单明手设计（DD/αμ 从未知牌池采样），天然适配实战 |
| 窜牌教训 | `docs/打牌窜牌诊断报告.md` | **并发打牌流程共享单例会窜牌** —— bot 必须用独立 play session |

### 1.3 现状差距（需要新写的部分）
1. **自动截屏**：现有流程需要人工 Win+Shift+S；bot 需要"整窗口定时自动截图"（PIL.ImageGrab 按窗口句柄 bbox 抓取，CLI 已有类似实现基础）。
2. **状态结构化**：把识别结果（我的牌、叫牌序列、已出牌、明手、定约、谁出牌）组装成引擎可用的内部状态。
3. **决策接入**：把结构化状态喂 BiddingService / PlayService，得到叫品/牌张。
4. **点击回写**：Win32 模拟鼠标点击桥友圈界面上的叫品按钮/牌张（**完全没有现成代码，是最大新模块**）。
5. **主循环与异常处理**：轮询 → 判定轮次 → 决策 → 动作 → 截图确认 → 防呆。

## 2. 技术路线对比

### 路线 A：截屏识别 + 模拟鼠标点击（**推荐，主路线**）
- **读取**：整窗口截图（PIL.ImageGrab，按 Edge 窗口 bbox）→ 豆包视觉识别（复用现有桥友圈 prompt 扩展）。
- **回写**：Win32 API（`SetCursorPos` + `mouse_event`）点击窗口内相对坐标。
- **优点**：完全复用现有识别管道；不依赖桥友圈 DOM 结构，网页改版/加密不影响；无需重新登录。
- **缺点**：桥友圈窗口必须可见（不能最小化/遮挡）；坐标需一次性校准；视觉识别有延迟（每次 ~2-5s，可接受）与小概率误差（用合法性校验兜底）。
- **风险控制**：识别结果必须通过引擎合法性校验（非法叫品/牌张 → 重识别或告警停止）；每步点击后截图确认状态变化。

### 路线 B：浏览器自动化（Playwright / dsh-browser 扩展）— 可选增强
- **读取**：DOM 直接取手牌/叫牌/出牌（精确、无视觉延迟）；**回写**：DOM click。
- **缺点**：Playwright 独立浏览器需要重新登录桥友圈（或有头模式 attach）；桥友圈 DOM/防自动化机制需逆向；dsh-browser 是 Chrome 扩展（Edge 可加载，但增加复杂度）；自动化框架本身可能被平台检测。
- **定位**：作为 A 的备选/增强（例如 A 识别定位不准时，用 DOM 辅助校准），不作为首发。

> **结论**：以路线 A 为主实施。理由：现有资产 90% 在 A 这一侧，A 与平台解耦、可持续性强；B 的登录态与反检测问题在练习桌场景收益不大。

## 3. 模块设计（新增 `bot/` 包）

```
bot/
├── config.py          # 桥友圈 bot 配置：窗口标题匹配、座位、引擎选择、轮询间隔、坐标校准偏移
├── observer.py        # 整窗口截图 + 豆包识别 → 结构化状态（见 3.1）
├── state_builder.py   # 结构化状态 → 本系统内部状态（叫牌序列 / PlayState）
├── decider.py         # 调 BiddingService / PlayService（独立会话）→ 决策
├── actuator.py        # Win32 模拟点击：叫品按钮 / 牌张，点击后截图确认
├── loop.py            # 主循环 + 状态机 + 异常/防呆
└── qyq_bot.py         # CLI 入口（python -m bot.qyq_bot）
```

### 3.1 结构化状态（observer.py 输出）
```python
@dataclass
class QyqObservation:
    phase: str              # "bidding" | "play" | "not_my_turn" | "table_closed" | "unknown"
    my_position: str        # 北/东/南/西（识别或配置）
    my_hand: list[str]      # 我的手牌（如 ["♠A","♠K","♥5",...]）
    bidding_sequence: str   # "(S)1H-(W)pass-(N)2C-" 格式（桥友圈叫牌表识别 → 引擎格式）
    contract: str | None    # 定约（打牌阶段）
    declarer: str | None    # 庄家位置
    dummy_hand: list[str]   # 明手牌（首攻摊开后才有）
    played_cards: list      # 已出牌墩（含本轮）
    current_turn: str       # 当前出牌人（识别）
    vul: str                # 有局情况（识别，影响叫牌）
    dealer: str             # 庄家/发牌人（叫牌起点）
```

### 3.2 决策接入（decider.py）
- **叫牌**：`BiddingService` 现有入口，喂"我方手牌 + 序列 + 座次 + 有局" → 返回叫品。复用主/备 prompt 与 JF 检索。校验：叫品必须合法（高于上一叫品、不重复等）。
- **打牌**：`PlayService.initialize()` 需要完整定约/角色；实战场景明手未摊开前或对手牌未知时，用**单明手初始化**（`bridge/play_engine.py` 的 `initialize` 已有部分手牌处理，参考"模拟实战"模式的人手未知逻辑）。决策引擎推荐：
  - 首攻/中盘：`dd`（Monte Carlo + DirectDDS，30s 内）或 `dd_alphamu_llm`（默认融合引擎，αμ 60s 上限，时间宽裕可用）。
  - 残局（≤8 张）：αμ 枚举或 DD 枚举（又快又准）。
  - 全程单座替打不涉及"双方视角"问题，引擎按**我方立场**决策即可。
- **独立会话**：打牌用独立 session_id（如 `qyq-<桌号>`），**绝不与浏览器练习页共用** PlayService 单例（防窜牌）。

### 3.3 点击回写（actuator.py）
- 窗口定位：按标题匹配 Edge 窗口（现有代码基础）→ 取窗口 bbox（`win32gui.GetWindowRect`）。
- 坐标模板：Phase 0 勘察后，为"叫品按钮区"和"我的手牌区"建立**相对坐标模板**（窗口内比例坐标，兼容窗口尺寸/DPI 变化）。
- 点击序列：置顶窗口 → `SetCursorPos` → `mouse_event(左键按下/抬起)` → 延时 → 截图确认。
- 防呆：点击后必须截图确认状态推进；两次失败 → 停止并醒目告警（不盲点）。

### 3.4 主循环（loop.py）
```
while True:
    obs = observer.observe()            # 截图 + 识别
    if obs.phase == "not_my_turn":      # 等待
        sleep(poll_interval); continue
    if obs.phase == "bidding" and 轮到我叫:
        action = decider.bid(obs)       # 叫品
    elif obs.phase == "play" and 轮到我出:
        action = decider.play(obs)      # 牌张
    actuator.click(action)              # 点击 + 确认
    sleep(短)                           # 等平台推进
```

## 4. 关键难点与对策

| 难点 | 对策 |
|---|---|
| 桥友圈叫牌界面布局未知（叫品按钮在哪、长啥样） | **Phase 0 勘察**：你提供 3 张截图（叫牌界面 / 出牌界面 / 明手摊开后），我据此定识别字段与坐标模板 |
| 视觉识别偶发错误 | 决策前合法性校验（非法叫品/牌张 → 重识别 → 仍失败则停止告警） |
| 误点/点错 | 点击后截图确认；连续失败即停；手动急停开关（如检测到窗口失焦） |
| 窗口遮挡/最小化 | 每轮前检查窗口可见并置顶；遮挡时暂停并告警 |
| PlayService 单例窜牌 | bot 独立 session_id（沿用已修复的会话隔离方案） |
| 明手未摊开阶段决策 | 打牌引擎按单明手采样未知牌池（DD/αμ 原生支持），明手摊开后自动切换完整信息 |
| 桥友圈为真实比赛平台 | 仅练习桌/好友房启用；正式比赛禁用；代码内置"练习桌模式"开关 |

## 5. 分阶段实施（每阶段有可验证里程碑）

- **Phase 0 勘察（需你配合，不写代码）**：你在 Edge 打开桥友圈练习桌，截 3 张图给我（叫牌界面、打牌界面、明手摊开后）。我据此确定：识别字段、叫品按钮坐标模板、手牌点击区模板。
- **Phase 1 状态读取**：整窗口自动截图 → 豆包识别 → 结构化状态。✅ 验证：识别出的我的手牌与实际一致。
- **Phase 2 决策接入**：结构化状态 → BiddingService/PlayService → 输出叫品/牌张。✅ 验证：CLI 单测，人工对照（不动浏览器）。
- **Phase 3 点击执行**：Win32 点击 + 截图确认循环。✅ 验证：练习桌开桌，你盯着看 bot 正确叫牌、出牌。
- **Phase 4 全自动**：主循环 + 异常处理 + 日志 + 急停；打完一整局自动核对结果。✅ 验证：完整一局 AI 替打成功。

## 8. 附：风险与边界
- **平台风控**：桥友圈为 CCBA 官方平台，即使练习桌，长时间固定模式自动化仍可能被关注；建议控制单次使用时长、避免高频操作。
- **识别延迟**：每步 2-5s 视觉识别 + 决策 15-60s，远低于分钟级时限，无压力。
- **坐标漂移**：窗口大小变化/系统 DPI 变化需重新校准；提供一键校准脚本。
