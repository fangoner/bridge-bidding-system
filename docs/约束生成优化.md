# 约束生成优化：回归叫牌真实产物

> 2026-08-28 定稿。本文记录叫牌约束生成从"叫牌阶段输出 + 规则库兜底"重构为"进入打牌统一生成"的全过程：来龙去脉、架构设计、具体修改、验证结果与决策记录。

## 一、来龙去脉

### 1.1 飞牌教训：约束是唯一杠杆

2026-08-26 定稿的 [教训_临界过滤与飞牌识别的废弃.md](教训_临界过滤与飞牌识别的废弃.md) 论证过：打牌引擎里所有"识别飞牌/干预选牌"的做法（临界分布过滤、镜像检测、保底优先、低张 tie-break）都是多余的——DDS 在给定世界内已是最优，飞牌难在"关键张位置推断"，而推断的正确性由**采样约束**决定。用户原话：*"如果做好约束生成，加上 DDS 本身的能力，足够打出飞牌的策略。"* 自此打牌引擎的改进重心转向约束质量。

### 1.2 规则库的三大问题

旧方案（v1.65 双通道）中约束来源包含 `bid_constraint_library.py` 规则库，实践暴露：

1. **不准确**：规则库是通用自然叫牌近似，比 JF / 新睿约定文档本身信息差太多；
2. **干扰叫牌过程**：规则库一旦接入叫牌，会污染后续叫牌 LLM 的判断上下文；
3. **泄露风险**：叫牌阶段同时输出"含义 + 约束"时，LLM 可能把真实手牌数据嵌入约束字段。

### 1.3 目标

- 约束**只来自叫牌阶段的真实产物**（LLM 叫牌含义结构化文本 + 约定原义），杜绝规则库兜底；
- 约束生成**绝不发生在叫牌过程**，统一在进入打牌的确认弹窗一次性完成；
- 约束承载**更多信息**：单缺花色、有控制花色（suit_controls）、关键张张数（min_keycards）。

## 二、架构设计

### 2.1 约束生成唯一入口：确认定约与首攻弹窗

```
打开"确认定约与首攻"弹窗
 ├─ buildBiddingInput(biddingSeq, aiHistory)
 │   ├─ 含义历史完整？→ 直接用
 │   └─ 无/不全（截屏/人工输入/历史导入）→ 新睿体系模拟人类叫牌补全含义
 ├─ POST /api/constraints（输入完整含义文本，公开信息，不含手牌）
 │   └─ 约束转换 LLM（CONSTRAINT_TRANSLATE_PROMPT）→ 各家约束 payload + 展示文本
 ├─ 弹窗显示"叫牌约束"区（loading / error / 各家约束展示）
 └─ 点击"确认" → doPlayInit(..., constraints) → PlayService._seed_constraints
```

- 弹窗按钮改为**「确认」**，约束生成期间禁用，保证进入打牌时约束已就绪；
- 无约束 payload 时后端兜底：`_get_bid_constraints` 用 `bid_meanings` 走同一 LLM 转译。

### 2.2 约束转换 LLM：完整历史 → 各家约束

`play_service.CONSTRAINT_TRANSLATE_PROMPT` + `generate_constraints_from_meanings(meanings_text)`：

- **输入**：完整叫牌历史每手每轮叫品的公开含义文本（含 pass，不含手牌）；
- **输出**：每个叫品对应一条"叫牌约束"串（结构化），同位置多次叫牌用 `_merge_constraints` **单调收紧合并**；
- **负面推断**：不叫 <12HCP；无 1 阶争叫 <8HCP 或无 5 张套；无 2 阶争叫 <11HCP 或无 6 张套；争叫位 pass ≤11HCP；
- **扣叫 → suit_controls**：扣叫花色记入有控制花色集合；
- **4NT/5NT 答叫 → min_keycards**：关键张只给张数（A+K 计数），不做具体花色承诺。

### 2.3 BidConstraint 扩展与校验

```python
@dataclass
class BidConstraint:
    min_hcp, max_hcp, balanced
    suit_min, suit_max, exact_suit
    min_controls
    specific_cards: Set[Tuple[str, str]]
    suit_controls: Set[str]   # 新增：有控制的花色（A/K 或单/缺，来自扣叫承诺）
    min_keycards: Optional[int] # 新增：关键张数量（4NT/5NT 问叫答叫）
    inference_source
```

`_check_constraint` 新增两维校验：

- **suit_controls**：该门持有 A/K，或该门 ≤1 张（单/缺即控制）；
- **min_keycards**：A+K 合计张数 ≥ 承诺数（一个关键张至少可分配 3-4 点用于范围推断）。

`relax_constraint` 放宽时：`min_keycards` 逐级递减；`suit_max/exact_suit/specific_cards/suit_controls/balanced` 放宽时不保留（碎片语义）。

### 2.4 叫牌阶段完全解耦

- 三个 LLM JSON Schema（主/备用/人类）**删除"叫品约束"字段**——叫牌阶段 LLM 只输出"叫品含义"，约束由弹窗统一转换，杜绝真实数据嵌入约束；
- 人类叫牌（JF 与新睿）**检索命中必走 LLM**；LLM 失败或 API 未配置 → 返回 error，`/api/human-bid` 抛 HTTPException(502) **中断叫牌**，绝不静默 pass 伪造成功；
- 前端"关闭 AI 解释"开关：含义置空（等价于缺失历史），进入打牌时按新睿模拟补全，与截屏/导入路径一致。

### 2.5 规则库身份改变

`bid_constraint_library.py` **保留文件、不接入系统**，仅作研究资产。依赖它的测试用例同步清理。

## 三、采样链路（约束如何生效）

```
PlayService._get_bid_constraints()
 ├─ _seed_constraints（弹窗 payload）→ _rebuild_bid_constraints 重建
 └─ 否则：bid_meanings → generate_constraints_from_meanings（LLM 转译）
      ↓
采样器 set_constraints → 每次决策：
  ├─ 中局扣减 _reduce_constraint_for_played（HCP/控制/花色张数按已出牌折算到剩余部分）
  ├─ void 硬事实（未跟花色即打缺，分配跳过 + L3 仅 void 验证）
  └─ 新字段天然相容：关键张/控制验证直接用剩余采样手牌计算（等价扣减）
```

- `suit_controls` / `min_keycards` 在验证时针对**剩余采样手牌**计算，已出牌不含在内，无需在 `_reduce_constraint_for_played` 额外处理；
- 展示层：弹窗各家约束 + 打牌决策输出的"叫牌约束"（整手）与"最新约束"（扣减后剩余部分）。

## 五、验证结果

- **`/api/constraints` 实测**：`1NT / pass / 斯泰曼2C / pass` → 南 15-17 均型、西/东 ≤11（负面推断）、北 ≥8（约定转译），LLM 约 2s 返回；
- **`/api/play/init` 三路径实测通过**：① 弹窗种子约束直用；② 无约束+含义文本 → 后端 LLM 转译；③ 无约束无含义 → 静默无约束不报错；
- **单元测试全绿**：约束合并、新字段校验（suit_controls/min_keycards）、采样约束满足率（1NT 82.5%、弱二 100%）；
- 前端编译通过（React `disableUnderline` 警告为既有 MUI 提示，与本次无关）。

## 六、决策记录（讨论要点）

| 议题 | 结论 |
|---|---|
| 什么时候没有生成约束？ | 进入打牌弹窗前统一保证：含义历史完整（无→新睿模拟），无约束场景仅剩"转换失败"（弹窗展示错误） |
| 检索命中是否走 LLM？ | **必走**。检索命中只提供约定原文，含义与约束均由 LLM 解释生成 |
| 备用提示词/检索不中的含义不精确怎么办？ | 不做单叫品约束（可能嵌入真实数据），用负面推断与累计承诺收紧 |
| 关键张信息长什么样？ | 仅在 4NT 问叫后提供，只有张数（数字），可换算点力（一个关键张 ≥3-4 点） |
| 控制怎么进约束？ | 扣叫承诺 → `suit_controls`（A/K 或单缺均可） |
| 规则库还留着吗？ | 文件保留作研究资产，**绝不接入系统** |
| 失败怎么办？ | 人类叫牌 LLM 失败/API 未配置 → 502 停牌，不静默 pass |
