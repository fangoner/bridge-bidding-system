# 桥牌练习系统全流程流畅性审查报告

> 审查范围：发牌 → 叫牌 → 打牌 → 定约完成 的完整链路（CLI 与 Web 双端，重点 Web）
> 审查方式：逐文件通读（`api/main.py`、`web/src/App.jsx`、`bridge/play_service.py`、`bridge/bidding_service.py`、`bridge/play_types.py`、`bridge/mcts/*`、`llm/*` 等）+ 4 个专项子代理交叉分析 + 关键路径实测
> 生成日期：2026-08

---

## 0. 结论速览

**总体评价**：系统功能完备、状态机设计有大量正确之处（打牌会话隔离、叫牌无状态化、undo 可靠、引擎时间预算、采样有界），但**"流畅性"存在系统性短板**：整条链路上有 **6 个 P0 级卡关点**（流程卡死或数据被悄悄写坏）、**11 个 P1 级长时间等待/明显卡顿点**。核心矛盾是**"后端一次 AI 决策 14~360 秒"这个现实与"前端 120 秒超时、无取消、无进度、失败静默"这个交互之间的断裂**。

**最堵的 3 个点**：

1. **后端事件循环被同步长任务阻塞**——`/api/bid`、`/api/image-deal`、`/api/double-dummy` 等 async 端点内直接同步调用 LLM/视觉识别（14~120s），单用户一次叫牌期间整个服务（包括健康检查和其他用户）全部冻结。
2. **AI 决策的等待与失败处理断裂**——前端 120s 超时 vs 后端单轮最坏 7.5 分钟；超时后 AI 叫牌**静默自动 pass** 写坏牌局；AI 出牌失败**无限重试循环**（默认引擎残局 αμ 阶段无异常兜底，一崩整局卡死）。
3. **流程衔接死胡同**——双人模式**没有打牌入口**；叫牌未结束可误入打牌并与在途 AI 叫牌交错；历史"进行中"牌局载入后强制显示为已完成、无法断点续打。

## 1. 流程链路与状态架构

### 1.1 主链路（Web）

```
发牌（随机/自定义/图片识别/截屏识别）
  → 显示手牌（可逐家输入/识别补全）
  → 开始叫牌（人类/AI 轮流；AI 每轮调 /api/bid，14-90s/轮）
  → 三家 pass 结束 → 自动保存叫牌记录 + 拉取输出格式
  → 点"切换到打牌" → 定约确认对话框 → /api/play/init
  → 首攻（图片识别带首攻信息则自动打出）→ 明手摊牌
  → 逐墩出牌（AI 自动出牌循环 / 人类点击；一墩完成自动暂停）
  → 13 墩完成 → 结果计算 → 自动保存完整记录
  → 复盘/倒回/重打/历史载入
```

### 1.2 状态架构评价（做对的部分）

| 设计 | 状态 | 说明 |
|---|---|---|
| 打牌会话隔离 | ✅ | `PLAY_SESSION_ID` 每标签页独立，后端按 session 存 PlayService，1 小时空闲回收 |
| 叫牌无状态化 | ✅ | `/api/bid` 每次传完整手牌+序列，服务实例按请求创建，不跨轮串状态 |
| undo 跨墩回退 | ✅ | `play_types.py:332-388` 递归恢复手牌/墩数/phase 正确，计划同步清理 |
| 引擎时间预算 | ✅ | MCTS 10s / DD 30s / αμ 8-60s，均有 deadline 检查，无死循环 |
| 采样有界 | ✅ | sampler 回退链固定次数（MH 300 + 50 + 20），αμ `_time_up` 已启用 |
| LLM 打牌兜底 | ✅ | `_validate_and_fallback` → `_select_best_card` 规则兜底，坏输出不会中断 |

## 2. 卡关问题清单（按严重程度）

### 2.1 🔴 P0 级：流程卡死 / 数据被写坏

#### P0-1 后端 async 端点内同步调用 LLM/视觉识别 → 阻塞整个事件循环
- **位置**：`api/main.py:372-491`（/api/bid）、`:254-295`（/api/human-bid）、`:1021-1104`（/api/image-deal）、`:1257-1344`（/api/read-clipboard）、`:1390-1436`（/api/double-dummy）、`:2085-2099`（/api/play/dd-hints）
- **问题**：这些是 `async def`，内部却直接同步调用 `bidding_service.ai_bid()`（14-90s）、`vision_client.read_cards_from_image()`（≤120s）、`analyze_all_contracts()`（秒级到数十秒）。FastAPI async 端点跑在事件循环上，**阻塞期间整个进程的所有请求全部排队**。对比：`/api/analyze-contract`（:603）和 `PlayService.get_ai_play`（`play_service.py:250-271`）已正确使用 `asyncio.to_thread`——说明这是遗漏而非设计。
- **影响**：单用户一次叫牌 60s 内健康检查都超时；多用户/多标签页时 A 用户在思考，B 用户的所有操作（出牌、截图、发牌）全部冻结，前端表现为"整个页面无响应"。
- **修法**：所有同步重活改 `await asyncio.to_thread(...)`；长任务演进为"后台任务 + job_id 轮询/SSE"；用信号量限制并发 LLM 调用。

#### P0-2 AI 出牌失败 → 前端无限重试循环，引擎一崩整局卡死
- **位置**：`web/src/App.jsx:2291-2325`（自动出牌两个 useEffect）＋ `:1986-1997`（handleAIPlay）
- **问题**：AI 回合先 `setAiThinking(true)` → 250ms 后 `handleAIPlay()`；失败时 `finally` 置 `aiThinking=false` → 2291 行 effect 检测到 false 立即再次置 true → 再调 `handleAIPlay`……**无退避、无次数上限**。每次重试都烧掉引擎全部时间预算（最长 60-90s）。
- **影响**：引擎持续失败时用户只见圆圈永远转，整局打不下去；唯一出路是手动暂停。
- **修法**：失败后进入"失败态"（连续失败 N 次即停），显示错误 + "重试"按钮；或指数退避 + 次数上限。

#### P0-3 αμ 引擎是唯一无异常兜底的引擎（且是默认引擎的残局阶段）
- **位置**：`bridge/play_service.py:787-874`（`_alpha_mu_play`）；对照 `_dd_play`/`_mcts_play`/`_llm_play` 均有 try/except 回退 `_select_best_card`
- **问题**：`_enumerate_endgame`（:803）与 `search.search`（:861）裸调用；`AlphaMuSearch.__init__` 中 `_load_dll()` 失败直接抛 RuntimeError。默认引擎 `dd_alphamu_llm` 的残局（≤8 张）阶段就是 αμ——**等于默认配置下半局有崩溃点**，崩溃后触发 P0-2 无限重试。
- **修法**：与其他引擎一致包 try/except 回退规则引擎；DDS 检查改为降级标志而非 raise。

#### P0-4 AI 叫牌失败被静默转成 pass，无提示、无重试 → 牌局被悄悄写坏
- **位置**：前端 `web/src/App.jsx:1088-1103`（callAIBid catch 分支直接 `addBid('pass')`，**未调 setError**）；后端 `api/main.py:482-491`（except 返回 HTTP 200 + `bid="pass"`，无 `success/error` 标志）
- **问题**：LLM 超时（前端 axios 120s）/网络错误/后端 500 时，前端写一条"AI叫牌异常"记录后照样落一个 pass 进叫牌序列。用户看到的只是一个毫无来由的 pass，且无法区分"AI 真选择 pass"和"AI 出错"。该 pass 污染后续叫牌推导与最终定约。
- **修法**：后端错误返回 4xx/5xx 标准结构或增加 `success/error` 字段；前端 catch 中 `setError(...)` 且**不自动落 pass**（或落 pass 同时弹"AI 异常已代 pass，可撤销"+重试按钮）。

#### P0-5 超时链条断裂：前端 120s vs 后端单轮最坏 7.5 分钟
- **位置**：前端 `web/src/services/api.js:7`（axios timeout=120s，系 2026 年从 30s 上调的既定决策，docs 已记录，见 §7.1）；后端 `llm/deepseek_client.py:128-132`（chat 30s / thinking 90-120s）+ `:162-239`（chat_json 2 次尝试 + 失败回落 chat() 共 3 次 HTTP）
- **问题**：一次 LLM 调用最坏 = 30×3=90s（chat）/ 90×3=270s（thinking flash）/ 120×3=360s（thinking pro）。叫牌单轮最坏调用链 = 主提示词 3 次 + 回退 2 次 = 5 次 LLM 调用 = **15 次 HTTP 请求** → 非思考模式最坏约 450s（7.5 分钟）、思考模式约 1350s（22 分钟）。前端 120s 一到就报错 → 触发 P0-4 静默 pass。
- **附带缺陷**：① `chat_json` 的 `schema` 参数**从未使用**（`deepseek_client.py:162-239` 无真实 schema 校验，只靠 `response_format=json_object` + 解析）——此点属**有意决策**（DeepSeek 不支持 `json_schema`，docs 已记录，见 §7.1），但由此带来的"LLM 返回不合规 JSON 只靠重试兜底"仍需正视；② **无指数退避**——`_is_timeout_error`（:158-160）是死代码，重试固定 `sleep(1)`；③ 重试对超时与业务错误一视同仁，超时后立即再试一次同样超时的调用。
- **影响**：单轮叫牌超 120s 时，AI 的真实结果被丢弃、牌局被写错；**且前端 abort 后后端线程（to_thread）不会被杀，继续跑满并消耗 API 配额**。
- **修法**：① LLM 调用加单次硬超时上限并**去掉 chat_json 的回落链**（JSON 失败直接返回错误，不要再用 chat() 补一发）；② 对超时/限流做指数退避，业务错误不重试；③ 前端超时与后端预算对齐或改"任务化+轮询"；④ 引擎内部做 deadline 检查实现可中断。

#### P0-6 DDS 库缺失时默认引擎"静默变笨"且无提示（打包/干净环境必踩）
- **位置**：`bridge/mcts/direct_dds.py:47-67`（`_load_dll`）；`bridge/mcts/dd_search.py:162-165`（`ENDPLAY_AVAILABLE = True` **硬编码**）；`requirements.txt`（无 endplay）
- **问题**：endplay 不在 requirements.txt。DLL 缺失时 DD 批量求解全部失败 → `samples_done=0` → 所有候选得分全 0 → **静默选第一张合法牌**（不报错）；αμ 直接抛异常（P0-3）；`ENDPLAY_AVAILABLE` 硬编码 True 掩盖不可用。
- **修法**：`_load_dll` 结果缓存为可用标志；DD/αμ/perfect 入口显式检测，不可用则报错或回退 LLM/规则引擎；`ENDPLAY_AVAILABLE` 用真实检测结果；requirements.txt 纳入 endplay 或给出降级提示。

### 2.2 🟠 P1 级：长时间等待 / 明显卡顿

#### P1-1 LLM 单步决策 14-90s 常态，最坏 91-361s；一墩最坏 6-18 分钟
- **位置**：`llm/deepseek_client.py:128-132, 162-239`；前端 `api.js:325`（aiPlay 超时 120s/300s）
- **影响**：LLM 打牌引擎下，一墩 4 家全 AI 最坏 ~6 分钟（chat）/ ~18 分钟（thinking）；整副 13 墩理论最坏 ~79 分钟。thinking 模式 60-90s/步是常态。
- **修法**：单次尝试 + 总超时上限（如 45s）后直接回落规则引擎；前端超时与后端预算对齐。

#### P1-2 默认引擎 αμ 阶段双重时间预算：枚举 30s + 搜索 32s
- **位置**：`bridge/play_service.py:803`（`_enumerate_endgame` 用 DD 的 30s 预算）＋ `:837-846`（αμ 自身 8-32s）
- **影响**：默认引擎残局单步最坏 ≈ 62s；纯 `alphamu` 引擎开局最坏 ≈ 90s。网页用户点一下等 1-1.5 分钟。
- **修法**：枚举与搜索共享一个总 deadline；枚举预算改小（如 10s）。

#### P1-3 `_get_bid_constraints` 的 LLM 约束提取：首步白烧 ~61s，结果被丢弃（死代码）
- **位置**：`bridge/play_service.py:741-781`（Step 3 结果只填进局部 `constraints`，函数最后 `return hard_constraints`，**LLM 结果从未返回/缓存**）
- **影响**：每局首次引擎决策可能先白等一次 `chat_json`（最坏 ~61s）；"LLM 补充约束"功能实际无效。
- **修法**：返回合并后的 `constraints`；或删除 Step 3。

#### P1-4 采样时间不计入 time_limit，约束不可满足时采样可能十几秒
- **位置**：`bridge/mcts/dd_search.py:472-487`（start_time 在 `sample_n` 之后）；`bridge/mcts/alpha_mu.py:352-353`
- **修法**：把采样阶段纳入总 deadline（如总预算 35s，采样最多占 5s）。

#### P1-5 DD 提示每次出牌连发无取消、无反馈（请求风暴）
- **位置**：`web/src/App.jsx:2231-2280`（useEffect 依赖整个 `playState`，每出一张牌/撤销即发 `/api/play/dd-hints`）；`api.js:380-388`（无 AbortController、无 debounce）；后端 `api/main.py:2050`（单线程无界队列，任务持整局深拷贝快照，DDS 无硬超时）
- **影响**：AI 连续自动出牌时后端被 DD 请求淹没；一次坏局面永久卡住提示线程；`ddHintsLoading` 只 set 不渲染，用户点开关后无任何反馈。
- **修法**：前端 300-500ms debounce + AbortController + 渲染 loading；后端队列有界、按墩去重、DDS 加硬超时、max_workers 提到 2-4。

#### P1-6 叫牌等待黑盒：无计时、叫牌侧无取消、"暂停"按钮不中止在途请求
- **位置**：`web/src/App.jsx:775-777`（toggleStopBidding 只翻转状态）、`:1087`（await 后无条件 `addBid`）；`api.js:86-112`（aiBid 无 signal）；`CardTable.jsx:836-838`（仅 22px 转圈）
- **影响**：AI 思考中发现叫错想中断，点暂停无效，结果照样落盘；14-90s 等待中无"已等待 N 秒"、无取消按钮，用户只能干等或刷新。
- **修法**：aiBid 加 AbortController；暂停时 abort 在途请求并标记"丢弃暂停前结果"；思考中显示计时与"取消本轮"按钮。

#### P1-7 截屏/图片识别无超时、进度用红色 error 样式、误关即静默取消
- **位置**：`api.js:176-186, 189-199`（裸 `axios.post` 无超时）；`useDealing.js:247-270`（`setError('截屏已触发…')`）；`App.jsx:2532`（任何 error 横幅 onClose 都置 `screenshotCancelledRef=true`）
- **影响**：豆包 Vision 异常时无限转圈只能刷新；进度显示为红底"错误"观感；用户误关任意错误提示即静默终止截屏轮询。
- **修法**：改用带超时的 api 实例 + AbortController；进度改 info/progress 样式；显式"取消截屏"按钮。

#### P1-8 双明手每次切换重复全量计算，无进度、无取消
- **位置**：`App.jsx:1403-1408`；`CardTablePanel.jsx:197-201`
- **修法**：结果缓存（手牌/叫牌未变直接复用）；加"分析中…"与取消。

#### P1-9 历史回放 52 次串行 playCard 无进度，失败静默
- **位置**：`App.jsx:1414-1528`（replayInitAndPlay 循环 await playCard）、`:1532-1563`
- **修法**：显示"正在载入已出 N/52 张…"；失败时 setError 并回退。

#### P1-10 全流程实测耗时：发牌→打牌结束 337s（开发文档 v1.59 记录）
- **位置**：`DEVELOPMENT.md:564`
- **说明**：这是"引擎全部正常"下的基线时长；叠加 P1-1~P1-4 的最坏路径后可达 10-30 分钟。用户对"打一副牌要 5-30 分钟纯等待"缺乏预期管理（无预计耗时提示、无"跳过/演示模式"）。

#### P1-11 /api/bid 的 except 块引用未定义局部变量 → 二次异常 → 裸 500
- **位置**：`api/main.py:482-491`（引用 `use_doubao`/`target_model`/`original_model`/`current_llm_client`，若异常发生在这些赋值前（如 `b['position']` KeyError）则 except 内抛 NameError）
- **修法**：except 前初始化默认值，模型切换/恢复放 try/finally。

## 4. 分环节专项发现

### 4.1 发牌环节
- 随机发牌（/api/deal）本地纯计算，无失败路径；自由发牌有 70% 概率把最强牌交换到南北——**默认行为会让学生牌局偏强**，属设计取舍，建议在 UI 明示。
- 自定义发牌解析失败返回 success=False + message，可恢复（OK）。
- 图片/截图识别：P0-1 阻塞事件循环 + P1-7 无超时/进度误导 + P2-11 假成功。**识别到的叫牌序列/定约/首攻解析较宽松，识别率不高（CHANGELOG 历史记录），需要用户在对话框人工确认——这是必经流程，但对话框交互已较完善**。
- 单家手牌识别（移动端/相册路径）存在，失败静默忽略（`useDealing.js:345-347`），可接受。

### 4.2 叫牌环节
- **关键词检索存在结构性空洞（实测确认；docs 已有长期讨论，见 §7.1）**：用真实 JF 文档实测，**"自然叫牌"关键词不在 JF 索引中**（文档无此章节）→ 大量中局序列（如 1H-2C-2H 再叫、自然叫牌路径）必走 fallback，且 fallback 注入的是无关的"成局与满贯"内容；同理"JF尚未实现"（1NT/高花 3 阶以上争叫、2NT 被干扰）场景注入内容与场景无关。这些轮次 = 回退提示词（质量低于主提示词）+ 至少 2 次 LLM 调用。注入"成局与满贯"本身是 docs 中用户确认的有意设计（见 §7.2），但"自然叫牌"无索引导致大量序列无条件落入该策略，覆盖不足仍是事实。
  - **修法**：① 补 JF 索引（"自然叫牌"等高频关键词）或改前缀/模糊匹配；② 为"JF尚未实现"场景准备场景化 fallback 内容（争叫后/被干扰后的通用应对），而不是一律注入"成局与满贯"。
- 回退提示词"总是返回有效叫品"且合规性检查会强制 pass，逻辑闭环（OK）。
- 合规性重试有反馈注入（"上次叫品非法"），但重试打满后单轮 = 5 次 LLM 调用（P0-5）；重试无指数退避、`_is_timeout_error` 是死代码（P0-5 附带缺陷）。
- 主路径 LLM 返回 dict 型"选定叫品"会崩溃（P2-28）；CLI 的 `_slam_cache` 跨牌局串状态（P2-26）；树解析深度栈失效拍平约定树（P2-27）。
- CLI 的 `BiddingGame` 与 Web 的 `/api/bid` 走同一 `BiddingService`，逻辑一致（OK）。
- **已验证无问题**：树导航/预处理全部为迭代实现、索引单调递增、无递归 → 无死循环/深度爆炸风险。

### 4.3 打牌环节
- 状态机（lead → dummy_reveal → playing → complete）流转正确；明手处理（`is_human_turn` 用庄家角色）正确。

## 6. 最堵的 3 个点（详述）

### ① 后端事件循环被同步长任务阻塞（P0-1）
这是最根本的堵点。叫牌（14-90s）、视觉识别（≤120s）、双明手分析全部同步跑在 async 端点里。单用户时一次叫牌期间整个服务无响应；多用户时任何一个人的长任务让所有人卡死。**修法简单且已有正确范例**（`asyncio.to_thread`），属于"做了就立刻不堵"的改动。

### ② AI 决策的等待与失败处理断裂（P0-2 + P0-4 + P0-5）
三条链路叠加：单轮最坏 7.5 分钟 > 前端 120s 超时 → 超时后静默 pass 写坏牌局；出牌失败后无限重试让整局卡死；等待全程黑盒（无计时、无取消、暂停无效）。用户最常遭遇的"以为卡死→刷新→数据丢/错"全部由此产生。**修法集中在错误语义 + 超时对齐 + 取消机制三处，投入中等**。

### ③ 流程衔接死胡同（P2-1 + P2-2 + P2-6）
双人模式没有打牌入口（叫完牌就结束）；叫牌进行中可以误入打牌并与在途 AI 叫牌交错；历史进行中牌局无法续打。用户在"发牌→叫牌→打牌→完成"主旅程上会撞到多个"此路不通"，且没有一个界面解释原因。**修法都是前端小改动，但直接决定主流程完整性**。
