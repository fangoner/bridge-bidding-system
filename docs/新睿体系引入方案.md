# 新睿（XR）二盖一叫牌体系引入方案与过程记录

> 本文档记录「新睿二盖一」叫牌体系从数据准备到前后端落地的完整引入过程、架构设计与决策。
> 数据构建细节见 [新睿全量重建方案.md](新睿全量重建方案.md)、[新睿体系树格式转换方案.md](新睿体系树格式转换方案.md) 与试点报告。

## 1. 背景与目标

现有系统使用 JF 叫牌约定（`llm/prompts.py` + `knowledge/jf_retriever`）。用户希望引入第二个完整体系「新睿二盖一」，与 JF 完全隔离，互不污染。

- 数据来源：《新睿实战 二盖一体系》文档（准确版，补充了 1C 开叫受干扰表与附录一索引）。
- 目标：LLM 依据新睿约定叫牌，输出行为与 JF 一致；前后端按「叫牌体系」下拉切换。
- 隔离原则：数据、检索、提示词、后端路由、前端 UI 均独立，不共用 JF 关键梳理。

## 2. 数据层

由 `scripts/xr_md_parse.py` 解析源文档、`scripts/xr_md_build.py` 重建 JF 风格树、`scripts/xr_validate.py` 校验，产出 `scripts/xr_data/md_tables.json`。

- **表格规模**：439 张表 / 450 条展开 seq，subsequent 全部正确解析。
- **附录一对齐**：对照 PDF 版附录一索引与正文表标题，补齐 12 张未收录表，人工发现 OCR 噪声（如表 2-151 实为 表2-15）不计缺失。
- **多叫品展开**：敌方括号内含多叫品（顿号/斜杠或共享阶数，如 `1NT-(2♣/♦/♥/♠)`）按笛卡尔积展开为多个独立 seq，实现精确命中。
- **迈克尔斯扣叫映射**：识别标题“迈克尔斯”关键词，将敌方扣叫花色修正为我方开叫花色的 2 阶（如 1H 开叫后敌方扣叫 → `(2H)`），规避源表标题 2♣ 笔误导致的 seq 错标。
- **seq 冲突处理**：同一 seq 多表（如 1H-(2C) 对应自然争叫 4-59 与迈克尔斯 4-63；1C(2C) 对应 2-73 自然/2-76 迈克尔斯）按 `_best_table` 最小表 id 规则消歧。

## 3. 检索层

`knowledge/xr_retriever.py`（`XrRetriever`）与 JF 完全隔离，独立加载 `md_tables.json`。

- **多 seq 索引**：由解析出的 seq 列表构建 `seq -> 表 id` 映射。
- **`_canon` 归一**：消除运行时 seq（`1NT-(2C)`）与索引 seq（`1NT(2C)`）的连字符差异，保证命中。
- **端到端命中验证**：1H-(2H)→迈克尔斯表、1NT-(2C)→6-41、1D-1H-(2C)→3-71、(1C)-X→11-13 等均命中正确表。

## 4. 提示词层

`llm/xr_prompts.py` 提供新睿三个提示词。**JF 与新睿不再各自维护一份提示词**，而是共用同一份共享模板生成，仅注入内容不同：

- **共享模板**（`llm/prompts.py`）：`_SHARED_SYSTEM_PROMPT` / `_SHARED_FALLBACK_PROMPT` / `_SHARED_HUMAN_PROMPT` 定义提示词全文，通过 `_make_prompt(template, system_tag, deal_system_block, no_valid_bid)` 参数化生成。
- **JF**：`BIDDING_SYSTEM_PROMPT` 等三件 = 共享模板 + `system_tag="JF"`、`deal_system_block=<阻击叫体系段>`、`no_valid_bid="JF无合格叫品"`。
- **XR**：`XR_SYSTEM_PROMPT` 等三件 = 同一共享模板 + `system_tag="新睿二盖一"`、`deal_system_block=""`（不渲染阻击叫体系段）、`no_valid_bid="无合格叫品"`。
- **唯一差异集中在注入内容**：体系名（`{system_tag}约定`）、是否含阻击叫体系段、无合格叫品文案，以及各体系自己的开叫/兜底约定片段。提示词正文逐字共用，不再分叉维护，保证 LLM 输出在通用规则上与 JF 完全一致。

- **主提示词 `XR_SYSTEM_PROMPT`**：注入当前玩家备选叫品列表，严格按叫品分类（简单新花/跳新花/扣叫/跳扣叫）识别 + 点力/张数严格匹配。
- **备用提示词 `XR_FALLBACK_PROMPT`**：无该 seq 备选叫品时兜底。其兜底约定 `XR_FALLBACK_CONVENTIONS` 直接采用最终 JF 文档「JF实战_标准自然 - Rev 3.2.docx」的「成局与满贯」片段全文（含 3.1 有高花配合速达、4.1 扣叫控制规则六步、4.2 RKCB、4.3 将牌Q/大满贯试探、4.4 特殊情况、4.5 DOPI/DEPO/R1P0），替代早期精简版，覆盖完整满贯探查细节。
- **人类叫牌 `XR_HUMAN_PROMPT`**：问将牌 Q 后答叫、扣叫上下文、将牌判定等规则。
- **共享模板恢复精确片段引用**：`3.1`（速达原则）、`4.1`（满贯门槛/扣叫控制）等编号已在共享模板内保留精确定位，指向注入片段对应小节，JF 与 XR 一并受益。

## 5. 后端集成

- `BiddingService` 同时注入 `jf_retriever` 与 `xr_retriever`，`api/main.py` 接收 `bid_system`（`"jf"` / `"新睿二盖一"`→`"xr"`）分流。
- 新睿主路径 `_ai_bid_xr`：由 `XrSeq.build` 生成 seq → `xr_retriever` 检索 → 主提示词；无备选或主提示词异常回退备用提示词。
- **开叫建议**：`/api/analyze` 开叫位置（seq 为空）注入 `XR_OPENING_CONVENTIONS`，与主叫牌流程开叫行为一致。
- **输出字段整改 `_xr_output`**：新睿输出的 `JF约定`→`XR约定`、移除 `阻击叫体系`，并将 AI 主/备用/人类各路径字段统一为 `XR约定`。
- **LLM 稳定性**：`max_tokens` 由 4096 提升至 8192，避免「逐一验证备选叫品」的长输出被 `finish_reason=length` 截断导致 JSON 解析失败。

## 6. 前端集成

- `SettingsPanel` 叫牌体系下拉：选「新睿二盖一」时隐藏「阻击叫牌体系」；状态存 `GameContext.bidSystem` 随请求透传（`aiBid`/`humanBid`/`analyze` 的 `bid_system`）。
- `BiddingDetailPanel` 标签与内容：以 UI 当前 `bidSystem` 为准（不依赖异步 suggestion），`JF`/`XR`、`JF约定片段`/`新睿约定片段` 随体系切换。
- **中心圆圈计时门控**：`playInitiated`（点击「开始打牌」）未置位时首攻 AI 不提前旋转计时；点击后才按当前玩家计时。

## 7. 验证结论

- 数据：md_tables.json 439 张表、validate `ERRORS:0`，附录一索引与正文完全对齐。
- 检索：关键干扰/扣叫 seq 端到端命中正确。
- 后端：XR 路径开叫注入、字段整改、max_tokens 提升后运行稳定，`_xr_output` 三种输入归一正确。
- 前端：体系切换后标签与内容即时联动；未开始打牌不再提前旋转计时。
- CI/运行：后端以无 `--reload` 启动加载最新 `md_tables.json` 与检索器代码生效。

## 8. 已知边界与待办

- 新睿数据覆盖以准确版源文档为准；后续新增表格需重跑 `xr_md_parse.py` 并重启后端。
- 同 seq 多表依赖 `_best_table` 最小表 id 规则，若后续出现需分流的新表需评估规则。
- 体系切换后需后端无 `--reload` 重启以加载最新数据/检索代码。
