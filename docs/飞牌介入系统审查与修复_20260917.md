# 飞牌介入系统审查与修复报告（v1.85，2026-09-18）

本报告记录对飞牌介入系统（`bridge/play_service.py` 飞牌段）的全面审查、用户定调与重构实施。方案文件 `.trae/documents/飞牌介入系统审查与修复方案.md`（已批准），本报告为实施后的归档总结。相关前序文档：飞牌讨论与修改记录_20260912/13、飞牌策略总整理、飞牌干预全流程图解。

## 一、审查背景

v1.77~v1.78 移除续飞流程、简化启动门控后，8飞9砸 与飞牌介入的边界遗留多处纠缠：跟牌侧 8/9 规则疑似死代码、9砸 判据在多处重复书写、`_nine_cash_done` 跨墩状态与 FIX-9"砸完退出"定调冲突。用户要求全面审查并给出方案，审查确认 6 个 bug 与 2 项已定调口径，随后用户批准实施。

## 二、审查发现

| 编号 | 问题 | 严重度 | 定性 |
|------|------|--------|------|
| BUG-1 | `_apply_eight_nine_rule`（跟牌侧 8/9 规则，153 行）内部重新探测飞牌结构，而跟牌时探针门控必然判空（`dd_search.py` 探针仅在领出侧生效）→ 恒为空、从未生效的死代码 | 高 | 删除整函数 |
| BUG-2 | 接应判定未校验领出方为我方——`_intervene` 仅我方领出时清空 flow，防守方领出时上一墩登记残留，"同伙任意位置出小牌"即触发强制接应 | 高 | 修复：`trick.cards[0]` 须为伙伴 |

| 架构-1 | 9砸 判据写两份（`_garrison_target` 与 `_nine_suit_should_garrison`），两处口径漂移风险（v1.66~v1.78 约束白名单事故同型根因） | 高 | 孤儿函数删除，判据唯一化 |

| 架构-3 | 三段 9砸 分流散落在 `_finesse_lead` 内，与飞牌介入主流程纠缠 | 中 | 抽出为独立分支 |

已定调口径（用户确认，保持不变）：
- **介入层分支化**：9砸 与飞牌介入为引擎结果之上的并列规则分支，先命中先赢；未来分支（忍让等）同接口并列加入
- **9砸 完全独立**：判据自含（联手张数+持张+对象未现+稳成线），零探针依赖；满手大牌场景探针 Δ 互偿趋零（DD 完美防守下大牌位置互偿，实测 ♠AK8765+♠432 缺 Q 场景单条 Δ 均 <0.1），而 9砸 判据不需要位置信息，独立分支零漏检
- **砸完退出**：AK 或 A 砸完后交回正常引擎和飞牌介入，无后续强制干预（连拔除外——连拔是已启动流程的完成动作，不受稳成线约束）
- **稳成时 9砸 退让**：全体候选最高做成率 ≥0.95 时不砸

## 三、介入层架构（v1.85 最终形态）

```
DD 引擎 search() → result
    ↓
_intervene(state, result, ratio)          # 总入口
    ├─ 非庄家方 / 垫牌 → 直接返回（信任引擎）
    ├─ 我方领出:
    │    清空 finesse_flow / flow_extra（登记只存活本墩）
    │    ├─ 分支1 _garrison_lead（9砸，FINESSE_EIGHT_NINE_ENABLE 门控）
    │    │    ① 连拔检查（nine_cash_bank，不受稳成线约束）
    │    │    ② 稳成线退让（_stable_make ≥ 0.95）
    │    │    ③ 四门按联手张数降序 → _garrison_target 判据
    │    │       A 在领出方 → 砸 A（缺Q持AK 登记 cash_bank 连拔 K）
    │    │       A 在伙伴手 → 引最小小牌 + 九砸标记（flow_extra 通信）
    │    ├─ 分支2 _finesse_lead（飞牌介入，FINESSE_DEFER_ENABLE 门控）
    │    └─ （未来分支：忍让等，同接口并列加入）
    └─ 跟牌:
         _garrison_follow（9砸跟牌：间张改 A）→ 接应链
         （_detect_finesse_struct → _registry_finesse_struct
          → _finesse_commit_check → _apply_finesse_commit）
```

跨分支通信：
- `finesse_flow_extra` "九砸" 标记：本墩信道——9砸 分支引小时写入，接应消费（顶张超吃）；领出=新墩清空
- `nine_cash_bank`：9砸 分支私有跨墩状态（`{花色: {obj, rv}}`），顺序砸 AK 的连拔登记；对象已现则清

关键判据口径：
- **对象**（missing-max，仅限 K/Q）：防家现手该花色最大牌 = 全牌面 − 联手现手 ∪ 已打出 − … 之最大。**2026-09-18 用户定调收紧**：对象仅限 K/Q 两种缺失——缺K持AQ / 缺Q持AK 才走 9砸；AKQ 顶张齐全（对象≤J，如联手缺 JT9）不走 9砸，交回引擎自然兑现
- **持张**：缺K（obj=K）须持 A+Q；缺Q（obj=Q）须持 A+K
- **间张**（跟牌侧改 A 的介入口径）：10 ≤ rv < 对象
- **稳成线**（FIX-7 统一）：`_stable_make` = 全体候选最高做成率（非仅榜首——榜首可能被位置信息误导）

## 六、教训

1. **死代码的隐蔽性**：`_apply_eight_nine_rule` 依赖"跟牌时探针恒空"这一远端门控事实，函数本身语法完整、逻辑自洽，只有跨模块追门控才能发现恒为死路径。判据依赖远端状态时应在入口断言。
2. **判据写两份必漂移**：9砸 判据双写（`_garrison_target`/`_nine_suit_should_garrison`）与 v1.79 约束白名单事故同型——规则唯一化（单一函数承载判据）是防漂移的根治手段。
3. **跨墩状态最小化**：`_nine_cash_done` 这类"流程进度"状态天然与"砸完退出"定调冲突；连拔改由 cash_bank（数据而非流程）承载后，状态机消失、行为可预测。
4. **实测场景要与判据逐条对账**：首轮实测 9砸 未命中，排查发现是测试场景构造错误（联手仅 8 张），分支行为反而正确。构造测试牌局时先核对判据每个条件（张数/持张/对象未现）再运行。
5. **探针 Δ 互偿是位置不敏感的物理上限**：满手大牌时 DD 完美防守下大牌位置互偿（东 8.62/西 8.54 级别的差异），探针无法区分方向——这不是探针缺陷而是信息论上限；9砸 判据恰好不需要位置信息，独立分支是正确解法。
