# LLM 分组审查功能有效性研究 & 整体优化方案

> 2026-08-08 调研。范围：`bridge/play_service.py` 的 `_llm_group_review` 及其调用链（`_dd_llm_play` / `_alphamu_llm_play` / `_dd_alphamu_llm_play`）。
> **核心目标：提高打牌水平（做庄 + 防守），而非加快出牌速度。**
> 前置约束：思考/非思考、模型选择由用户手动控制，程序不做默认干预。

---

## 一、当前机制

### 1.1 引擎调度（主力引擎 = dd_alphamu_llm）

```
get_ai_play(use_reasoning)
  └─ _dd_alphamu_llm_play
       ├─ 手牌 > switch_cards(默认8) → _dd_llm_play     (DD 采样 + LLM 分组审查)
       └─ 手牌 ≤ switch_cards        → _alphamu_llm_play (αμ 搜索 + LLM 分组审查)
```

两阶段共用 `_llm_group_review`，差异仅在分组依据：
- **DD 阶段**：按「各 world 赢墩数向量完全相等」分组（`_group_candidates_by_tricks_vec`）
- **αμ 阶段**：按 best_vector（成约向量）分组（`_group_candidates_by_vector`）

### 1.2 审查触发条件（做庄方：`_should_trigger_llm` + 调用点前置判断）

做庄方（庄家/明手）审查**必须同时**满足：
1. **分组数 ≥ 2**（有选择空间）
2. **成功率差距未一边倒**（Q5 触发门槛精细化）：
   - DD 阶段：`diff < 1.645·SE`（SE=√(p(1-p)/N)，N 为实际采样数，采样少放宽、采样多收紧），无采样数时回退固定 0.15
   - αμ 阶段：`diff < 0.35`（`ALPHAMU_LLM_GAP_CAP`），只拦明确一边倒的罕见局面
   - 绝望模式：所有候选成功率=0 且 ≥2 组 → 用 `_build_desperation_groups` 重分组后触发
3. 候选列表非空

**防守方独立审查**（`_run_defender_review`，在做庄门槛判断之前分流，不受做庄门槛影响）：
- 触发克制：仅关键防守墩（跟同伴领出、垫牌、将吃抉择）经 `_is_key_defense_trick` 判定
- LLM 出牌必须落在赢墩等价组内，否则回退引擎选择

### 1.3 审查决策

- LLM 读取手牌/叫牌/已完成墩/关键大牌/将牌统计/分组信息，输出 JSON：`{group, plan, steps, plan_valid, reason}`
- **默认选第 1 组**（= DD/αμ 引擎首选），除非发现非第 1 组有「第 1 组做不到的关键战术」（飞牌/将吃/进张/长套/终局）
- **组内选牌：机械 min/max**——当前玩家=明手 → 选最小；否则 → 选最大
- 审查结果跨墩存入 `self.declarer_plan`，后续墩 `_check_plan_invalidation` 校验失效后重制
- 调用 `chat_json(temperature=0.3, thinking=use_reasoning)`

## 二、有效性评估（关键数据）

### 2.1 延迟成本巨大（审查是打牌响应瓶颈的核心）

来自 `deepseek_debug.log` 实际日志（3143 次请求，打牌 866 次）：

| 模型·模式 | 成功次数 | 平均 | 中位 | 最大 |
|-----------|:---:|:---:|:---:|:---:|
| FLASH·思考 | 127 | 43.2s | 33.9s | 126.4s |
| FLASH·非思考 | 722 | 7.7s | 7.8s | 16.5s |
| PRO·思考 | 12 | 120.5s | 126.1s | 174.2s |
| PRO·非思考 | 5 | 59.9s | 23.9s | 208.8s |

思考模式比非思考慢 5~15 倍。**可靠性上，选牌/防守比选组更依赖推理**，非思考快答大概率机械处理——因此 Q1/Q3 按"用户开思考"为前提设计。

### 2.2 大量「空输出」：付出巨延迟却无决策

日志中 `finish_reason=length` 且 `response=0` 的思考模式调用非常多（8KB reasoning token 耗尽、可见输出 0）。根因是思考模式：推理链先耗尽 `max_tokens`，轮不到生成答案。`chat_json` 解析空 → 返 `{group:0}` 兜底 → **审查空转，用户白等 30~120s**。

### 2.3 审查被设计为「默认选组 1」→ 实际覆盖很少

- 强一致性约束 + 15% 门槛 → 审查多数时候验证引擎选择，而非改进
- 价值主要体现在「引擎成功率接近、需战术判断」的边缘局面

### 2.4 决策质量无线上对照基准

- 没有「DD/αμ 首选 / LLM 覆盖 / Perfect DD 最优」批量对比
- 无法量化审查到底改善了多少做庄质量 → 有效性无法被证明

### 2.5 三个结构性短板（有效性的真正瓶颈）

| 短板 | 说明 |
|------|------|
| **不选具体牌** | 组内机械 min/max，丢弃信息获取/进手/终局价值 |
| **计划是文本** | 计划存 raw_text + steps，失效/完成靠大牌子串匹配，粗糙易误判 |
| **防守无人把关** | 防守占一半决策，完全跳过审查，且无信号机制 |

## 三、整体优化方案（核心目标：提高打牌水平）

> 统一原则——**引擎守"赢墩正确性"，LLM 在"赢墩等价"约束内优化"过程"**（进手/信息/终局/信号）。所有 LLM 出牌必须落在引擎判定的赢墩等价组内，由程序硬校验兜底，**赢墩永不损失**。

### Q1：LLM 决定具体牌张（做庄）——不只选组

**原则**：在「引擎保证赢墩等价」的约束内，把张张之间在信息/进手/终局上的差异交给 LLM 优化。

- **现状**：选定组后组内机械 min/max（明手最小/其他最大）
- **问题**：DDS 等价组内不同牌张在「信息获取、保留进手、终局管理、伪装」上价值不同，机械选牌丢弃这些机会，是 DDMC「non-informative play」缺陷在审查层的残留
- **做法**（智能在提示词、接线在程序）：
  - 提示词加「组内选牌」段：三原则——①进手管理（这墩由庄家还是明手赢）②信息隐藏（出哪张泄露最少）③终局保留（哪张留到最后）
  - 输出 JSON 加 `card` 字段
  - 程序校验：`card` 必须在所选组 + 可出牌内；否则回退机械 min/max
- **收益**：直接提升单墩出牌质量
- **实现状态**：✅ 已落地。新增 `_resolve_group_card`（校验 LLM `card` 在组内+可出，否则回退机械选牌），αμ/DD 两处选牌均接入；提示词加「组内选牌」段、JSON 加 `card`

### Q2：结构化跨墩计划——替代文本+子串匹配

**原则**：把 LLM 给的路线从"人类读的散文"升级成"程序能逐墩校验执行的结构"。

- **现状**：plan 存 raw_text + steps，失效检测/步骤完成靠「大牌子串匹配」——只扫文字里有没有出现某张牌，无法判断"进手张是否被逼出""飞牌目标位置是否证伪"
- **问题**：计划往往一边执行一边失效，多墩路线形同虚设
- **做法**：每个 step 存结构化战术实体
  ```
  {step, action, play_card, precondition, tactic,
   target_card, entry_card, ruff_suit, completed}
  ```
  - `_normalize_step` 兜底 LLM 漏字段
  - `_mark_step_completed` 用 `play_card` 精确匹配落桌
  - `_check_plan_invalidation` 改为对照 `entry_card`（是否被逼出且已不在己方手中）/ `target_card`（是否已出）精确校验
- **收益**：多墩战术规划真正贯穿全副，避免"每两步就作废重来"
- **实现状态**：✅ 已落地。新增 `_normalize_step`（结构化实体兜底）；`_build_plan_from_review` 每步规范化；`_mark_step_completed` 优先 `play_card` 精确匹配、回退 action 子串；`_check_plan_invalidation` 用 `play_card`/`target_card`/`entry_card` 精确校验、无结构化字段时回退大牌匹配；提示词 steps 模板与 `_format_plan_for_prompt` 均支持结构化字段

### Q3：审查覆盖防守方 + 信号机制

**原则**：防守选牌的核心是**在不损失赢墩的前提下传递信号**。赢墩是硬约束，信号是赢墩等价组内的软选择。

- **现状**：防守方出牌完全跳过审查（`current_player not in (declarer, dummy)`）
- **问题**：防守占一半决策，跟牌信号/垫牌/将吃时机/非领出防守无人把关；且现有 `signals.py` 只做**被动解读**（读同伴信号），无**主动发信号**能力
- **做法**：
  1. 新增 `_defender_llm_review` + `_run_defender_review`：防守方也走赢墩等价分组，但评估方向反转（目标最小化庄家赢墩数）
  2. 提示词加「防守信号」段：**赢墩硬约束优先**（只能在赢墩等价组内选牌），在此前提下传信号——跟同伴领出欢迎大牌/不欢迎小牌、垫牌花色偏好、张数标记
  3. 注入同伴已发信号（复用 `format_partner_signals_for_prompt`）
  4. 程序硬校验：最终出牌必须落在赢墩等价组内，否则回退机械选牌 → **信号永不牺牲赢墩**
- **收益**：代入双方视角，防守质量提升
- **触发克制**：只在关键防守墩（跟同伴领出、垫牌、将吃抉择）触发，避免每墩引入开销
- **实现状态**：✅ 已落地。新增 `_is_key_defense_trick`（关键防守墩判定）、`_defender_llm_review`（防守提示词+信号段+同伴信号注入）、`_run_defender_review`（赢墩等价组内选牌，复用 `_resolve_group_card` 硬校验，非法回退引擎）；αμ/DD 两处防守方出牌改走审查，程序硬校验保证**信号永不牺牲赢墩**

### Q5：触发门槛精细化（低成本，微调）

- αμ 阶段 `gap_threshold=None`（≥2 组必触发）→ 改为「组间成功率差 < 0.35 才触发」，只拦一边倒的罕见局面
- DD 阶段固定 15% 阈值 → 依据实际采样数 N 自适应：`diff < 1.645·SE`（SE=√(p(1-p)/N)），采样少放宽、采样多收紧，参考 `dd_card_selection_discussion.md` 的动态 SE 思路
- **收益**：减少「无需判断的审查」，避免打牌水平高的局面被无谓审查拖累

## 四、建议的实施顺序

按「直接提升打牌水平」的杠杆排序：

1. **Q1（LLM 选具体牌，做庄）** —— 单墩质量，改动局部、见效最快
2. **Q3（防守审查 + 信号）** —— 补齐半边，覆盖面最大；先做阶段1（跟牌/领出 + 逆分值分组），再做阶段2（注入同伴信号），阶段3（分场景）
3. **Q2（结构化计划）** —— 多墩路线，工程量大
4. **Q5（触发门槛精细化）** —— 基于数据微调

> 建议首次落地：**Q1 + Q3 阶段1**，验证"审查确实提高了成约率/防守质量"，再推进 Q2/Q5。

## 五、关键取舍汇总

| 权衡 | 处理 |
|------|------|
| 信号 vs 赢墩 | **赢墩硬约束绝对优先**，信号只在赢墩等价组内选择，程序硬校验兜底 |
| LLM 负责什么 | 判断战术意图/信号意图（懂牌理），程序保证赢墩合法性 |
| 思考模式 | 由用户手动控制；Q1/Q3 按"开思考"设计，触发频率克制 |
| 防守信号模块 | 现有 `signals.py` 管"读"，Q3 新增的是"发"（出牌时选信号牌张） |
| 正确性兜底 | 所有 LLM 出牌必须落在赢墩等价组内，否则回退机械选牌，永不丢赢墩 |
