# 打牌窜牌 / 非法牌 问题诊断报告

日期：2026-08-13
状态：**已确认根因，已复现，已按方案 A 修复并验证通过**

---

## 1. 现象

- 打牌过程中，引擎偶尔返回"不属于当前玩家手牌"的牌（例如 ♦6 在西手却让南出），导致出牌失败。
- 该问题在此前从未出现，仅在引入**后台 API 批处理脚本**（`_headless_batch.py`）后出现。

## 2. 根因（代码证据）

`api/main.py` 中，打牌服务是**进程级全局单例**：

```python
play_service = None

def get_play_service():
    global play_service
    if play_service is None:
        current_llm_client = get_llm_client()
        play_service = PlayService(current_llm_client)
    return play_service
```

- `/api/play/init`、`/api/play/card`、`/api/play/ai-play` 等所有接口都拿这**同一个实例**。
- 无会话隔离、无 per-request 作用域、无锁。
- `PlayService` 内部维护一份**可变**的 `state.hands`（每局四家手牌）。

## 3. 并发如何产生"非法牌"（关键机制）

`ai_play` 内部对 DD/αμ 计算用了 `await asyncio.to_thread(...)`，这会**让出事件循环**。于是：

1. 请求 1 的 `ai_play` 开始 DD 计算（耗时数秒），期间仅持有 `state` 快照。
2. 请求 2 的 `play_init` 在计算窗口期内执行，**覆盖共享 `state.hands`**（换成了另一局的手牌）。
3. 请求 1 计算完成后，用旧的 `state` 得出结论，随后调用 `play_card` 时，却从**已被覆盖的新 `state.hands`** 校验合法性。
4. 结论：请求 1 返回的牌不属于"新当前玩家"的手牌 → 判定为**非法牌**。

即：**并发覆盖共享状态 → 出牌校验用的是被改乱的另一局手牌 → 窜牌/非法牌。**

## 4. 并发复现（已执行）

脚本 `_repro_concurrency.py`：先初始化游戏 A 并触发 `ai-play`，在 A 的 DD 计算窗口期内用游戏 B 覆盖服务。

```
[A] init ok, current_player=西        ← 游戏 A 初始化
[B] 覆盖 play_init (游戏 B)            ← DD 窗口内 B 覆盖了共享服务
[A] ai-play success=False card=♥T     ← A 出牌失败（♥T 已不在当前状态）
```

复现成功：A 的 `ai-play` 返回 `success=False`，与线上"非法牌"现象一致。

## 5. 为什么以前从未发生

- 此前**只有一个消费者**：浏览器里单个用户、单局游戏，`state.hands` 从不会被第二个流程覆盖。
- 引入后台 API 脚本后，出现了**第二个并发打牌流程**（脚本 + 浏览器，或脚本内部并发的两局），共享同一单例，触发覆盖。
- 单用户单局时，`state.hands` 始终是干净的 52 张，非法牌路径不会走到。

## 6. 多用户支持现状

**当前系统不支持多用户/多局并发。**

- 打牌服务为全局单例，一次只能承载一局。
- 若两个用户（或一个用户 + 后台脚本）同时打牌，必然互相覆盖 `state.hands`，产生窜牌。
- 这是架构层面的单局假设，不是偶然 bug。

## 7. 影响范围

- 多用户并发打牌：必然窜牌。
- 单用户 + 后台自动化脚本并行：窜牌。
- 单用户单局：不受影响（此前一直正常的原因）。

## 8. 已做的临时修复（保留，作为纵深防御）

- `bridge/mcts/sampler.py`：`_extract_known_info` 去重改为在**局部副本**上进行，不再写回调用方的 `state.hands`。
- 作用：防止采样器把"已被并发污染、含重复牌"的手牌进一步改乱。**未解决并发源头**，只是降低二次污染。

## 9. 修复方案

### 方案 A：会话隔离（推荐，彻底）
- 打牌服务按 `session_id`（或用户/连接）隔离，各自持有独立 `PlayService`。
- 接口带 `session_id`，服务端维护会话注册表 + 生命周期清理（超时/断开回收）。
- 前端每局生成一个 session；后台脚本同样带上自己的 session。
- 优点：真正支持多用户/多局并发，逻辑清晰。
- 改动：后端 API 分层 + 会话管理 + 前端传参，改动较大。

### 方案 B：单机加锁（简单，治标）
- 给 `play_service` 加 `asyncio.Lock`，同一时刻只允许一个打牌流程。
- 优点：改动小。
- 缺点：并发用户会被阻塞，仍是单局，不符合多用户预期。

### 方案 C：仅保留纵深防御
- 保留 sampler 修复，不处理并发。适合"确认只有单用户使用"的场景。
- 风险：一旦多用户/脚本并行，仍会窜牌。

## 10. 建议

- 若近期要支持多用户或后台并行测试，采用**方案 A**。
- 若仅单用户使用，可先维持现状 + sampler 修复，待有并发需求再升级。

## 11. 实施记录（方案 A 已完成 2026-08-13）

**后端**（`api/main.py`）：
- 移除全局单例 `play_service`，改为会话注册表 `_play_services: Dict[session_id, (PlayService, last_ts)]` + `threading.Lock`
- `get_play_service(session_id="default")`：按会话取/建独立 `PlayService`，LLM client 复用全局 `get_llm_client()`（不随会话新建，性能无影响）
- 所有 `/api/play/*` 接口（init/card/undo/ai-play/set-hand/update-roles/state/dd-hints/particle-settings）均支持 `session_id`（POST 走 body，GET 走 query）
- 生命周期清理：`@app.on_event("startup")` 启动后台 asyncio 清理任务，空闲 1 小时（`_PLAY_SESSION_TTL`）自动回收会话

**前端**（`web/src/services/api.js`）：
- 模块级 `PLAY_SESSION_ID`，每浏览器标签页独立一个后端会话，注入所有打牌请求

**后台脚本**（`_headless_batch.py`）：
- 每副牌用独立 `headless_board_{n}` 会话，互不干扰

**验证**：
- 并发复现：修复前 A 返回 `success=False`（非法牌）；修复后并发下 A 仍 `success=True`，会话隔离生效
- 单机流程：`_headless_batch.py` 2 副牌完整跑通（4S 10墩、1NT 7墩），`DONE ALL BOARDS`
