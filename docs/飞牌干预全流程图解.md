## 〇、总览：干预在出牌链路中的位置

```
AI 出牌请求（/api/play/ai-play）
  │
  ▼
PlayService.get_ai_play()                                    [play_service.py:218]
  │  引擎分发（flag 由 API play_engine 参数决定）
  ├─ use_perfect ──────► _perfect_play()          :3706   ✗ 无飞牌干预
  ├─ use_dd ───────────► _dd_play()               :3647   ✓ 有（受 DD_FINESSE_ENABLE 门控）
  ├─ use_alphamu ──────► _alpha_mu_play()          :986   ✓ 有（无 DD 开关，仅总开关）
  └─ use_dd_alphamu_llm ► _dd_alphamu_llm_play()  :1212   ← 默认主力
         │ 按每手剩余牌数分流（DD_ALPHAMU_SWITCH_CARDS=8）
         ├─ cards > 8  → _dd_play()       → ✓ 干预（DD 探针法）
         └─ cards ≤ 8  → _alpha_mu_play() → ✓ 干预（αμ 模板法）
  │
  ▼
引擎返回 result {card, reasoning, full_output{..., mcts_stats{candidates}}}
  │
  ▼
_apply_finesse_tactics(state, result, FINESSE_RATIO)         [play_service.py:2641]
  │  ← 唯一干预入口，DD/αμ 共用
  │  ← 决策依据全部来自 result.full_output.mcts_stats.candidates
  ▼
最终 card（可能已被改写，rewrite 记录写入 full_output）
```

**关键事实**：干预发生在**引擎选牌之后**，是叠加在引擎之上的规则层。引擎永远先给出 `candidates`（含 `scoring_val`）与 `card`，干预只做「改写或放行」。

**引擎识别法分流**（`_detect_finesse_struct` :2528）：

| 引擎 | 结构来源 | 判据 |
|------|---------|------|
| DD | **探针法** | `full_output` 含 `finesse_probe` 键 → 只信探针；探针为空 = 无结构，**不回退模板法** |
| αμ | **模板法** | 无 `finesse_probe` 键 → 回退静态间张识别（方法B） |

## 一、闸门层：什么时候根本不干预

```
_apply_finesse_tactics(state, result, ratio)                 [:2641]
  │
  ├─ ① current_player ∉ (declarer, dummy)？ ────► 放行（防守方出牌完全不干预）
  ├─ ② FINESSE_DEFER_ENABLE == False？ ────────► 放行（总开关，同时关掉接应/窗口期/流程）
  │
  │  ── 仅庄家/明手方出牌继续 ──
  ├─ ③ _is_discarding(state)？                 [:2625]
  │     本墩已有领出，且本家手中无领出花色（只能垫）
  │     ────► 放行（垫牌只需垫好，不做任何飞牌处理）
  │
  └─ ④ 区分出牌场景
        ├─ _is_leading(state) == True  [:2621]  本墩尚无任何牌（自己是第一家）
        │     └─► 【领出路径】 §二
        └─ 否则（跟牌）
              └─► 【跟牌/接应路径】 §三
```

> **隐含闸门（DD 专属）**：`dd_search.search` 中
> `_probe_ok = (not trick_cards) and (actual_turn in (declarer, dummy))` [:658, :990]
> 探针**只在「庄/明手正在领出」时生成**。跟牌/垫牌时探针为 `None` → `finesse_probe` 键不存在 → DD 走模板法？**不**：DD 路径下 `_detect_finesse_struct` 检测的是「键是否存在」，跟牌时键根本不存在 → 回退模板法。
> v1.71 的探针门控修正正是为了防「滑动窗口下移发明飞 T 对象」，代价是跟牌时 DD 结构识别退化为模板法（**变更时需注意的口径不对称**）。

### 2.1 窗口期启动的三路分流（`_probe_lead_finesse_prefer` [:3287]）

```
遍历 finesse_struct 每个花色 s：
  跳过条件： _nine_cash_done(s)   → 已砸A，走 9砸后续
            cur_str[0] == s       → 引擎已在飞牌花色，尊重
            suit_cands 为空       → 领出方无该花色可出

  combined = _combined_suit_count(state, s)      # 联手张数 = 在手 + 我方已出
  │
  ├─ combined ≥ 9（9张：砸/飞分流）
  │    │
  │    ├─ _nine_suit_should_garrison(state, s, obj) == True   [:3273]
  │    │    = (obj==K ∧ 有A ∧ 有Q) 或 (obj==Q ∧ 有A ∧ 有K)
  │    │    → 【应砸】bank = candidates 中 rank > obj 的牌
  │    │       取其中最大顶张，why = "9砸优先（出顶张砸）"
  │    │
  │    ├─ 否则 _has_high_suit_cards(state, s, leader, (14,12)) == True（顶张方）
  │    │    → 【应飞 · 顶张方】reentry = _cash_reentry(...)
  │    │       ├─ 成功 → 出无关小牌回手，why = "顶张方回手队友侧飞"
  │    │       │         state.finesse_flow[s] = obj          ← 写流程标记
  │    │       └─ 失败 → continue（换下一花色 / 最终 None = 尊重引擎）
  │    │
  │    └─ 否则（非顶张方）
  │         → 【应飞 · 非顶张方】small = candidates 中 rank ≤ 9
  │            ├─ 非空 → 出最小飞张小牌，why = "非顶张方直接飞小牌"
  │            │         state.finesse_flow[s] = obj          ← 写流程标记
  │            └─ 空 → continue
  │
  └─ combined < 9（8飞：只飞不砸，不做 garrison 判定）
       ├─ 顶张方 → 同上「回手队友侧飞」分支
       └─ 非顶张方 → 同上「直接飞小牌」分支
```

> **门槛设计要点**：窗口期启动**不走 `FINESSE_RATIO`（0.95）比值**。比值评估的是「这张牌 vs 引擎榜首」的单步值，顶张恒高于飞张小牌，会系统性扼杀所有主动启动（单步贪心看不到跨墩收益）。启动依据是**探针结构本身**（Δ ≥ `FINESSE_PROBE_DELTA` = 位置敏感）。

### 3.1 `_finesse_commit_check` 判据表（威胁比较制）[:3505]

```
前置不满足 → None（尊重引擎）：
  无 current_trick / 本墩无牌 / fs 为空
  current_player ∉ (declarer, dummy)                ← 仅庄家方
  同伙未在本墩出该花色 rank < obj 的牌（launch 为空）  ← 飞牌未启动
  本家无该花色合法跟牌（suit_cards 为空）

▼ 判定顺序（自上而下，命中即返回）

① 敌方本墩已出 ≥ obj
     covers = suit_cards 中 rank > obj
     covers 非空 → 出 covers 中**最小**顶张        「盖K/Q/J」
     covers 为空 → None（尊重引擎）

② _finesse_obj_played(state, suit, obj) == True
     （对象在历史墩已现身，飞牌已完成）→ None      尊重引擎兑现，不贴小牌作伪接应

③ below = suit_cards 中 rank < obj
     below 为空 → None（本家无飞张可贴）

④ 威胁计算（剩余牌推断，敌方两家 = 全部牌面 − 我方庄/明现手 − 本墩已出 − 已完成墩）
     guarded = [14..2] 中不在 present 且 ≠ obj
     threat  = max(guarded)，无则 0

     ├─ partner_rv > threat（同伙引牌已大过敌方全部非对象剩余 → 引牌方可赢）
     │    → 出 suit_cards 中**最小**牌                 「引牌已胜，最小跟」
     │
     └─ 否则（须第三家打大牌保本墩）
          above_threat = suit_cards 中 rank > threat
          ├─ 为空 → None（本家无牌可压威胁，尊重引擎）
          └─ 非空 → 出 above_threat 中最小
                      block = suit_cards 中 rank>obj 的最大者（仅用于提示）
```

> **尊重引擎的唯一途径（v1.71）**：`_finesse_commit_check` 返回 `None`。比值退让（`<0.90`）已于 2026-09-09 删除——比值是采样口径（对象位置敏感），不能否决已确定的结构动作。

### 3.2 8飞9砸（`_apply_eight_nine_rule` [:3377]）

```
门控： FINESSE_EIGHT_NINE_ENABLE == True
       result.card 花色 ∈ finesse_struct（当前决策牌已非结构牌 → 不介入）
       len(candidates) ≥ 2
       top_val = 引擎榜首的 scoring_val（≤0 则退出）

联手张数 trump_cnt = |在手| + |我方该花色已出|（含垫牌/跟牌/本墩已出）
  ← 「按墩结算」：首墩按在手+本墩已出计 9 张，后续扣已出

should_garrison 判定：
  obj == K → trump_cnt ≥ 9 ∧ 有A ∧ 有Q     （缺K持AQ → 先砸A再飞Q）
  obj ≠ K  → trump_cnt ≥ 9 ∧ 有A ∧ 有K     （缺Q持AK → 砸）

▼ 候选筛选
  should_garrison == True（9砸，规则优先，**不受比值保护限制**）
     候选需：rank > obj（顶张） ∧ 榜首 rank < obj ∧ ≥10（飞张）
     取 val 最大者 → why = "9砸"；若 obj==K ∧ ¬(A∧K) → why = "9砸先飞"
  should_garrison == False（8飞，软干预，**受比值保护**）
     候选需：10 ≤ rank < obj（飞张） ∧ 榜首 rank > obj（砸张）
     且 (cand_val / top_val) ≥ ratio（FINESSE_RATIO=0.95）
     取 val 最大者 → why = "8飞"

▼ 命中 → 改写 card，写 full_output["八九原则"]
         full_output.pop("飞牌接应")   ← 清除接应残留提示，避免界面自相矛盾
  未命中 → 原样返回（尊重引擎）
```

## 四、状态机：`finesse_flow` 跨墩标记

`state.finesse_flow: Dict[花色, 对象rank数值]`，是**唯一的跨墩记忆**。

```
                 ┌─────────────────────────────────────────┐
                 │  写入（启动那墩）                        │
                 ├─────────────────────────────────────────┤
                 │ · _probe_lead_finesse_prefer 回手/直飞分支 │
                 │ · _apply_lead_transfer 过手成功           │
                 │ · _apply_flow_continuation 隐式启动       │
                 │   （结构花色对象未现 ∧ 我方曾领出过该花色）│
                 └───────────────┬─────────────────────────┘
                                 │ finesse_flow[s] = obj
                                 ▼
        ┌────────────────────────────────────────────────────┐
        │  每次领出时 _apply_flow_continuation [:2932] 接管    │
        ├────────────────────────────────────────────────────┤
        │ ① 隐式启动补充（见上）                              │
        │ ② 清理（仅两条硬判据，与当墩探针无关）：             │
        │      _finesse_obj_played(s,obj)  → 对象现身，删除    │
        │      _finesse_suit_dead(s,obj)   → 我方已无 >obj 的 │
        │                                     上方控制，删除   │
        │ ③ 若活跃流程为空 → return False（交回上层）          │
        │ ④ 逐流程算 (mode, pick, val)：                       │
        │      lead_ctrl = 领出方手中有 >obj 的牌              │
        │      ├─ lead_ctrl ∧ _has_finesse_reentry_high        │
        │      │     → mode="回手"，reentry=_cash_reentry      │
        │      │       无回手牌 → 该流程跳过                    │
        │      ├─ cur_str[0] == s（榜首已在飞）                │
        │      │     → mode="正在飞"，尊重引擎（仅记录状态）     │
        │      └─ 否则                                          │
        │           队友该花色无牌 → 跳过（无法接应续飞）        │
        │           候选无 ≤9 小牌 → 跳过（手上无牌可续飞）      │
        │           → mode="续飞"，出最小飞张小牌               │
        │ ⑤ 取 val 最大的流程执行；全不可行动 → 尊重引擎        │
        │     （写 full_output["领出飞牌"]={引发:False,…}）     │
        └────────────────────────────────────────────────────┘
                                 │
                    写 full_output["飞牌续"] / ["领出飞牌"]
```

> **设计纪律**：流程存活**不依赖当墩探针**。Δ 是采样量，探针一时判空不代表流程结束；否则顶张侧回手后探针判空会把流程误清、飞牌中断（6♠ 例北被放行乱出的根因）。
>
> **分层纪律（v1.71）**：`finesse_flow` 只管**下一墩领出**（回手/续飞）；**接应判据绝不与流程混层**——接应严格只信当墩探针，不用 flow 补构。

## 七、八条易踩陷阱（改动前必读）

1. **DD 跟牌时无探针**：`_probe_ok` 要求「本家领出」，跟牌无 probe 键 → DD 结构识别回退模板法。口径与领出不对称。
2. **接应不做二次检测**：`_apply_finesse_commit` 与 `_finesse_commit_check` 必须共用同一 `finesse_struct`，内部重新检测会静默吞掉已确认结构（6♠ ♠8 被吞根因）。
3. **接应禁止用 flow 补构**：flow 只管下一墩领出，接应只信当墩探针（2026-09-09 撤销）。
4. **9砸不受比值保护**：`should_garrison` 为真时跳过 `val/top_val ≥ ratio` 检查，是确定打法。
5. **窗口期启动不走比值**：启动依据是探针 Δ，不是 0.95。
6. **回手只适用于顶张方**：`lead_ctrl` 用 `> obj` 判定（飞 K 时持 A 才算顶张；持 Q 是飞张侧，应继续飞）。9飞第二轮北持 ♠Q 被误判回手的 bug 即此。
7. **垫牌不处理**：`_is_discarding` 直接放行，且垫牌不计入 9砸张数减少（初始联手张数口径）。
8. **流程清理只看两条硬判据**：对象现身 / 花色已死，与当墩探针无关。

## 八、时序示例：9张缺K持AQ（先砸后飞 → 回手 → 续飞）

```
墩 n    南（顶张方，持 AQ）领出
         探针 Δ≥0.4 识别 ♠(K) → 窗口期
         _nine_suit_should_garrison(♠, obj=K) = (有A ∧ 有Q) = True
         → 【应砸】改出 ♠A（"9砸优先"）
         ← 此路径不写 finesse_flow（砸是终结动作，先把 A 兑现）

墩 n+1  K 未落 → _nine_cash_done(♠) = True（A已出 ∧ K未现 ∧ 联手≥9）
        南（顶张方）再领出：
          nine_suits=[♠] → leader_high=True（持 Q）
          _cash_reentry(♠) → 找队友稳赢花色的最小小牌 → ♥4
          → 强制改出 ♥4 回手，写 full_output["9砸回手"]

墩 n+2  北（非顶张方）领出
         _detect_finesse_struct 仍报 ♠(K)（对象未现）
         _nine_cash_done(♠) 仍 True → leader_high=False
         → 强制改出 ♠ 最小飞张小牌，写 full_output["继续飞牌"]
         （同时在流程延续层写/续 finesse_flow[♠]=K）

墩 n+3  对象 K 现身（被飞中或被打出）
         → _finesse_obj_played 为真 → 流程清除，交回引擎
```
