## 二、实验一：成功率口径 vs 平均墩口径（结果推翻了预期）

在 4♥ 例牌（南♥AKJT98+北♥32，残局7张/手，飞牌决策点北♥3-东♥4-南跟）重采样 5×400 世界：

| 口径 | 拔♥A | 飞♥J | 首选 |
| --- | --- | --- | --- |
| 平均墩 | 6.327 | 6.210 | 拔A |
| 成功率(≥10墩) | 28.2% | 19.0% | **拔A** |

- **关键结论：换成功率口径不能救飞牌**。2000 世界分类：J独胜=102、A独胜=286（2.8倍）。拔A失败常惜败9墩，飞J失败连9墩都保不住——均匀先验下拔A确实期望更优。
- **路线条件化才是关键**：条件到"飞牌可成"世界集（J成+J独胜=380）时，飞J 100% vs 拔A 73.2% → 飞牌登顶。人类坐庄本质是"把世界条件化到能成约的分布"，引擎是"均匀先验期望最大化"。
- 脚本：`scripts/_success_rate_compare.py`（成功率/平均墩/条件化四类分析）。

## 三、识别方法之争：方法A（冲突检测）失败，方法B（静态间张）成功

- **方法A（冲突检测）**：候选对逐世界成败向量互斥（你成我败/我成你败都>0）→ 飞牌结构。实测**只在 L2（飞牌点）检出，L1（北首出）零检出**——因为 L1 时飞牌牌（♥J）在庄家手中不在候选里，检测失效。作废。
- **方法B（静态间张，用户提出）**：合并庄家+明手每花色，从高到低找"可飞对象"缺失大牌 M（K/Q/J）；有上方控制张（>M）+ 下方≥T飞张 + 合计≥4张 → 该花色可飞。缺A/缺≥3/大牌齐全/无飞张不飞。**23/23 用例通过**（`scripts/_finesse_structure_chklist.py`），真实牌局精确识别 ♥ 缺Q。
- **教训**：飞牌结构识别必须在"决策前"静态完成，不能依赖候选内互斥——飞牌主角经常不在当前出牌人的候选里。
- 方法A脚本：`scripts/_finesse_detect_test.py`（两方法对比）。

## 十一、启动判定放宽与接应选牌修正（2026-09-02）

### 用户指正的核心规则
1. **启动判定**：同伙出**任何 < 对象**的牌都算启动飞牌（包括 Q 找 K、J 找 Q、T 找 J 等间张引牌），不再限于 ≤9 小牌。
2. **接应选牌**：
   - 敌方已出对象大牌（≥对象）→ 用**最小的高于对象的顶张**盖掉
   - 敌方未出对象：
     - 同伙领出 ≥10（Q/J/T 间张引牌）→ 出**最小**的低于对象的牌（不浪费飞张，如 AJx 中出 3 不出 J）
     - 同伙领出 <10（小牌找飞）→ 出**最大**的低于对象的牌（贴住对象的飞张，如 AJx 中必须出 J）

### 代码修改（`_finesse_commit_check`）
- **启动判定**：`rv < finesse_struct[suit]["对象"]`（替代原 `rv <= 9`）
- **接应选牌**：新增敌方出牌检测（`enemy_top`），按"对象是否已现 + 同伙领出大小"三分支：
  1. `enemy_top >= obj` → 出 `min(covers)`（最小顶张盖）
  2. `partner_rv >= 10` → 出 `min(below)`（最小飞张，保 J）
  3. `partner_rv < 10` → 出 `max(below)`（最大飞张，贴对象）

### 识别层跨花色串味 bug 修复（同日）
`_detect_finesse_struct` 原实现把**所有花色**已打出的 A/K/Q/J rank 混进同一个 set（`played_ranks`），再并入每个花色的 present——导致 **♠Q 打出会抹掉 ♥ 的"缺 Q"识别**（跨花色串味，漏报飞牌结构）。

修复：改为 `played_by_suit: {花色: set(rank)}` 按花色分别记录，present 只并入**同花色**的已出大牌。

验证（`scripts/_finesse_commit_verify.py` 新增 ⑫）：♠ 与 ♥ 各自缺 Q → 均识别；♠Q 打出后 → ♠ 消除（Q 已现），♥ 仍识别（不受影响）✅；23/23 结构用例回归通过。

## 十四、飞牌启动重构（2026-09-07 ~ 09-08，v1.70 主体）

> 本轮把飞牌干预从"识别→拖延→接应→续飞"改为"**探针检测 + 显式验证 + 窗口期主动启动**"三层，并废弃整个拖延策略。核心问题：单步贪心看不到跨墩飞牌收益；方向性（谁先出/谁过手）与值问题（出哪张）是两个维度。

### 14.1 拖延策略废弃（用户决策）
- **理由**：坐庄方明手牌可见、防守方为采样平均，引擎单步贪心不会因拖延换花色"获得信息后改判"——拖延只有代价无收益。
- 删除：`_defer_candidates`、`_is_danger_suit`（护张保护随拖延废弃一并删除）、`_is_finesse_struct_card`、入口领出拖延分支；配置 `FINESSE_RATIO_RISK`/`FINESSE_LOSE_TRIGGER`/`FINESSE_DEFER_WIN_MIN`。
- **纠错**：9/7 只删了配置，方法与领出分支当时仍残留（`_defer_candidates`/`_is_danger_suit`/`_is_finesse_struct_card`），9/8 才全部清干净。教训：**删功能要一次删完**（调用点+方法+配置），不要分批。

### 14.2 窗口期主动启动飞牌（`_probe_lead_finesse_prefer`）
- 探针识别出结构（Δ≥0.4）即"窗口期"：此刻飞最有价值。领出方为庄/明手、引擎榜首是其他花色时，主动改出该花色路线启动飞牌，避免"顶张先打完、窗口关闭后飞牌无收益"的死锁。
- **门槛关键决策：不走 0.95 比值**——0.95 评估"这张牌 vs 榜首"的单步值，单步贪心眼里顶张恒高于飞张小牌，会系统性扼杀所有主动启动；探针 Δ（分桶均值差）本身是跨墩度量，可直接作启动门槛。
- 分流：联手≥9 → 按砸/飞分流（应砸出顶张；应飞顶张方回手、非顶张方直飞）；<9 → 只飞不砸，顶张方无稳赢回手牌则不强制（尊重引擎）。
- 输出 `full_output["窗口期启动"]`。

### 14.3 顶张侧过手启动（`_apply_lead_transfer`）
- 方向性问题：顶张方（持 A/Q）自己领出该花色方向错误——出顶张是砸、出间张烧结构，飞牌须由无大牌的队友侧首次引飞。
- 触发：当前侧探针未识别结构时，"假设从队友侧出一次牌再探测"——真的以队友为领出方跑一次 DD 评估（`dd_search.search(state, perspective=partner, actual_turn=partner)`，新增覆盖参数），取队友侧 `finesse_probe`。
- **口径一致性：队友侧探测也是探针法 + 同一 Δ≥0.4 门槛，模板法只归 αμ 引擎**（用户明确要求，不许用模板放水）。
- 结构成立 + 当前方是该花色顶张方 + 队友有飞张小牌（<对象）+ `_cash_reentry`（原 `_nine_cash_reentry` 更名统一）有稳赢过手牌 → 改出无关花色小牌过手给队友 → 写 `finesse_flow` 标记 → 此后由流程延续正常接管。
- 输出 `full_output["领出过手"]` / `领出飞牌.引发=True 说明=顶张侧过手启动`。

### 14.4 流程标记对象化（finesse_flow 存对象）
- **根因**：finesse_flow 原存"进行中"字符串，`_apply_flow_continuation` 清理逻辑用"当墩 finesse_struct 缺失"→ 判空 → 直接清除流程。顶张侧回手后探针一时 Δ<0.4，流程被误清 → 飞牌中断（6♠ 例回手后北被放行乱出）。
- 修复：写入时存对象 int（`state.finesse_flow[s] = obj`）；清理只按"对象现身 / 花色已死"判定，与当墩探针无关。
- 配套：`_apply_lead_finesse_check` 探针空时若 flow 有活动仍先走流程延续，再试过手，最后才"无飞牌结构"。

### 14.5 探针法：分桶敏感性 + Δ 阈值 0.4
- DD 引擎飞牌识别**只用探针法**：probe 键存在（无论是否为空）只用探针结果，判空即无飞牌结构，不回退模板法（模板法会误判"缺K即可飞"，如南直接领出 Q 的假飞场景）。
- **阈值 0.5→0.4**：基于真实触发时点（游戏进行中我方赢下上一墩后领出）实测调整——8张样本平均 Δ=0.76、9张平均 Δ=0.86，原 0.5 使 8/9 张识别近乎全线失能。
- **教训（测试时点）**：在"整副初始+强改 current_player"下测试探针会系统性压低 Δ 值；正确测试应在真实触发时点进行。

### 14.6 可飞性校验（`_probe_struct_playable`）：探针检测 + 显式验证两层
- **问题**：探针 Δ 高只说明"位置敏感"，不必然构成可飞结构。6NT 例探针报 ♠T Δ=0.4 压线，被误当飞牌结构强改出 ♠2——但 ♠ 联手只有 AK+小牌，没有任何 <T 的间张，无张可飞，只能是砸兑现。
- 校验：我方现手（庄+明）该花色须有**可飞间张（<对象 且 ≥10）** 与**上方控制（>对象）**，否则跳过该花色。
- **主路径与顶张侧过手路径同口径共用**（过手路径此前从队友侧探针构建结构时漏了该校验，同类假结构 ♥K32+AQJ 缺 T 也会触发过手，seed42 实测抓到）。

### 14.7 探针 3 张滑动窗口（修正固定 AKQJT 五张集）
- **用户设计原意**：默认检测对象是 AKQ；出掉一个、下移补一个（出掉的就不检测），一直保持检测三张牌。例：飞 K 且 K 已出 → 窗口变 AQJ；A 也出 → 变 QJT。这样残局阶段小牌（J/T）也能被飞，自然扩展飞牌范围。
- **实现偏差教训**：上轮把"动态下移"扁平化实现为固定 5 张集 `{A,K,Q,J,T}`，每个花色一次性监控全部缺失大牌——违背了"3 张滑动窗口"语义，且对所有花色一律下移，导致 ♠AK+xx 缺 T 类"J/T 位置敏感"假阳性（♠T Δ=0.4 压线误报）。
- 最终实现（`dd_search._honor_missing_of_state`）：
  - 非飞牌花色：窗口固定 `[A,K,Q]`（打出即排除、不补位）
  - 飞牌花色（`state.finesse_flow` 中活动流程的花色）：窗口取 AKQJT 中前 3 张未打出者，出掉一张、下移补一张
  - **下移只针对飞牌花色，不作用于所有花色**
- 配套：删除失效 `_R2V_PROBE`；`play_types.finesse_flow` 类型标注更正为 `Dict[str, int]`。

## 十五、接应选牌"威胁比较制"（2026-09-08 同日晚）

### 15.1 问题：旧判定按同伙引牌大小分三档 + 10 分界，会烧回手间张
原 `_finesse_commit_check`：
- 同伙引 <10（小牌找飞）→ `pick = max(below)`（贴最大低于对象者）。例：对象 K、同伙引 ♦7、接应方持 ♦QJ3 → 贴 ♦Q——把本可留作回手再飞 K 的 Q 烧掉（09-08 早晨刚实现 `_has_finesse_reentry_high` 依赖该间张），与"保留结构"冲突。
- 同伙引 ≥10（间张引牌）→ `pick = min(below)`，未区分小牌(2-9)与间张(≥T)。
- 全程不查"对象是否已现身"（被拿下/打出 → 飞牌已完成，仍贴小牌 = 伪接应）。

### 15.2 用户规则（废除 10 分界，改威胁比较）
> 领出启动飞牌后，第二家（防守方）未用对象盖住时：
> - 若同伙引牌 > 敌方剩余牌中除对象外的 **最大牌（威胁）** → 顶张方出最小牌（保留结构）
> - 否则 → 顶张方出 **大于威胁的最小牌**（第三家打大牌，保住本墩）

### 15.3 实现（`_finesse_commit_check` 重写）
判定顺序（关键！）：
1. **敌方本墩已出对象** → 最小顶张盖（"对象现身"在此是盖牌动作，必须处理）——必须在"对象历史已现"检查**之前**
2. **对象历史墩已现身**（被拿下/打出）→ 飞牌已完成，不贴小牌，尊重引擎兑现
3. 否则计算 **威胁 = 敌方剩余牌中除对象外最大者**（剩余 = 全部牌面 2..14 − 我方庄/明现手 − 本墩已出 − 已完成墩已出）：
   - 同伙引牌 > 威胁 → 出最小牌保留结构（"引牌已胜，最小跟"）
   - 同伙引牌 ≤ 威胁 → 出 >威胁 的最小牌；**无牌可压 → 尊重引擎（None）**

范围注意：选牌从全部可打牌中取（不限 below）——压威胁需要时可以动用高于对象的牌；盖分支本就出 covers。

### 15.4 中途 bug（测试暴露）
初版把"对象已现身 → 不接应"放最前，误伤"本墩敌方刚出对象、需要盖牌"的场景（用例：西 ♦K、南持 ♦AQ3 应出 ♦A 盖，却返回 None）。修复：**盖分支在前，历史对象已现检查在后**。

### 15.5 跟牌接应侧 flow 补构（同口径对称修复）
跟牌分支原只信当墩探针（`_detect_finesse_struct`），探针是采样量、一时判空会中断接应——与领出侧"流程延续"（finesse_flow）不对称。修复：`_apply_finesse_tactics` 跟牌分支 `fs` 为空但有活动 `finesse_flow` 时，用 flow 对象补构结构再判接应。
（**【2026-09-09 已撤销，见第十六章 16.3】**）

### 15.6 验证

### 19.1 多结构启动：合并→排序→逐个门控（用户定调）

### 19.2 "假结构过滤"被否决（重要教训）
起初试图按"联手无高于对象的牌 → 假结构"加过滤，用户直接否决：

- 结论：**不加假结构过滤**，只做用户要求的多结构 Δ 排序。假 Q 判据（A/K 均已出、无间张支点）已从记忆与文档删除。

### 19.3 流程终结：为什么用 finesse_flow_ends 而非"清理先行"
问题：对象 A 现身 → `del flow["♦"]` 正确触发，但**下一轮**隐式启动又用滑动窗口的新对象 Q 重建流程（`_our_side_led_suit` 历史领出恒真）。

## 二十、经验教训（v1.72~v1.73）

1. **不做自认为合理的扩展**：用户要求"只加排序"就只做排序；真假结构过滤先讲清规则、确认后动手，确认选项必须忠实用户原话。

3. **流程终结要防"滑动窗口复活"**：对象现身是硬终点；后续重新启动须有新的行为证据（重新领出该花色），不能靠滑动窗口的新对象自动复活。

### 22.3 约束转译"联手点力"口径：37 不是北单人 HCP
界面出现"北 HCP ≥37 均型"，但南 2NT 已承诺 20-21。37 是**联手点力**（南 20-21 + 北 ≥16 合计约 37），LLM 转译北 7NT 含义"联手点力达到37点以上"时把联手总点写成了北个人 HCP，经 `HCP37+` 解析为 `min_hcp=37`。

危害不止显示：约束进入采样后北被要求持 37 点（几乎不可满足），`_reduce_constraint_for_played` 还按 37 扣减已出点力（37−18→≥19），进一步污染世界。

修复（`CONSTRAINT_TRANSLATE_PROMPT` 规则 2，用户定调分流）：
- **[XR]/[JF]**（非 AI，约定含义可信）：含义给出联手下限 X 且注明同伴 HCP 区间 → 推导本家下限 = X − 同伴区间上限（北 7NT：37 − 21 = **HCP16+**）。
- **[AI]**：一律禁止推导，HCP 留空。
- 任何情况不得把联手总点直接写为任一家个人 HCP。

实测：南 HCP20-21 均型保留；北从"HCP ≥37 均型"→ 先修成"均型"→ 定调后可推导为 **"HCP ≥16 均型"**。

### 22.4 比值退让统一：做成率优先、决策值兜底（两段式）
缘起：强制接应在赢墩制下把"♣K 100% / ♣6 0%"强推改出 ♣6——三处飞牌干预里**唯独强制接应无比值退让**（2026-09-09 注释明确"威胁比较制选出牌则一律强制，不再按决策分比值退让"）。

第一版用决策值比值（scoring_val），被用户否决：**赢墩制 13 vs 12 比值 0.923 ≥ 0.75 不退让，但 13 是唯一成约（7NT），12 全宕**——决策值比不出成败差距。

定稿 `_finesse_ratio_ok`（统一判据，三处+续飞/回手共用）：
- **段1 做成率**：`success_rate`（αμ）/ scores 相对 `tricks_needed` 达成占比（DD），双方可算且参照>0 → 比值 < ratio 退让。
- **段2 决策值兜底**：参照做成率≤0（双方均无成约希望）或成功率数据缺失 → `scoring_val`→`avg_tricks`→scores 平均 比值 < ratio 退让——**宕深浅/超墩在此层保留计分制感知**。

应用与阈值：窗口启动 D 闸 `FINESSE_NEC_RATIO=0.90`；强制接应/8飞9砸/续飞/回手 `FINESSE_RATIO=0.75`。

用户关于"计分制存在的意义"的解答：计分制主要职责在**引擎决策层**（榜首选择与候选排序，imp=稳健优先/宕分矩阵、make_rate=成约优先、avg_tricks=多拿墩），飞牌比值退让是**目标达成护栏**（成败视角、跨计分制通用）——两层正交；差悬殊的边界（无法成约时宕深浅）由段2决策值兜底保留计分制价值。

### 22.5 窗口启动：榜首在结构花色时尊重引擎
案例：D 与 C 都探出飞牌结构、D Δ 更大、引擎榜首已是 ♦Q（26.5%），日志却"改出♣3启动（契约必要：榜首做成27%，不飞没机会）"。

根因：`_probe_lead_finesse_prefer` 按 Δ 降序遍历，D 在前但 `cur_str[0]==s → continue` 仅**跳过**榜首花色，随后 C 通过退让门控（"契约必要"成立）→ 误启动 ♣3。

修复：榜首已落在**任一飞牌结构花色**（本侧+伙伴侧合并池）→ 直接 `return None` 尊重引擎；删除循环内"跳过榜首花色继续尝试下一个"的 continue。验证：榜首 ♦Q → 尊重引擎出 ♦Q；榜首 ♠K（无关花色）→ 按 Δ 降序启动 D 而非 C。

### 22.6 流程清除双原则：`_finesse_flow_dead`
案例：♦ 飞 K 流程进行中，第 4 墩北（明手）**♦A 已出**，第 4 墩"续飞"仍把榜首 ♣Q(56.6%) 强改 ♦9；此后现手南北 ♦ 只剩 J、T——联手已无高于 K 的牌，**飞 K 无意义**，但 flow（对象 K 未现身）未清。

用户定调：**"清除飞牌标志要有两个原则，一是对方被飞对象已出，二是己方可以盖过被飞对象的牌已出。目前应该只有第一条。"**

实现 `_finesse_flow_dead`：① 对象已现身（被打出/砸落，既有）；② 己方联手现手已无高于对象的牌（上方控制张全出 → 对象成该花色最大，飞无可飞）→ 流程终结。应用到 `_apply_flow_continuation` 清理段（删 flow + 记 `finesse_flow_ends`）与 `_merge_finesse_flow`（跟牌接应侧结构来源过滤，防已死流程继续驱动接应）。真局验证：♦A 已出 → flow 清除、续飞不再干预（引擎出 ♣）；♦A 仍在明手 → 流程保持有效。

### 22.7 续飞/回手补比值退让（用户："补上吧"）
续飞与回手此前是最后两个无比值退让的流程动作（2026-09-10 注释"不设软指标"）。案例：榜首 ♣Q 56.6% vs 续飞 ♦9——差距巨大仍强改。补上 `_finesse_ratio_ok`（b_card=引擎榜首）后：20% vs 57%（比值 0.35 < 0.75）→ 尊重引擎；50% vs 57%（0.877 ≥ 0.75）→ 保持强制续飞。

至此所有飞牌干预点（窗口启动/强制接应/8飞9砸/续飞/回手）全部接入统一两段式退让。

### 22.8 流程迁移：比值退让后实际出牌落在另一结构花色（用户提出）
案例连续两墩暴露"流程脱节"：第 4 墩南领出，flow=♦(K)；续飞 ♦9（做成率 19.1%）对榜首 ♣Q（57.7%）比值 0.33 < 0.75 **退让** → 尊重引擎出 ♣Q（♣ 也是探针结构花色）；但 flow **仍为 ♦**。第 5 墩续飞又强改 ♦9（58.5% vs ♣3 75.2%）——流程与实际路线脱节。

用户原话：**"上一墩由于比值退让，选了 CQ，而 C 也是飞牌花色之一，那么当时就应该取消 D 飞牌标志，而赋予 C 飞牌标志。现有程序不会做这个动作。"**

实现（`_apply_flow_continuation` 尊重引擎分支）：所有流程花色均无行动（比值退让/无牌可续）且引擎实际出牌落在**飞牌结构池的另一花色**（非已在流程、且该花色流程未死）→ **迁移**：取消原花色 flow（记 `finesse_flow_ends`）、登记实际出牌花色 flow（用结构对象）。此后下一墩：榜首已属新流程花色 → "正在飞"尊重引擎，不再强改旧花色（♦9 案例闭环）。

验证（真局数据复现，♣ 对象=K、北手 ♣A 可压）：第 4 墩退让后出 ♣Q，flow `{♦:13} → {♣:13}`，`finesse_flow_ends={♦:0}` ✓；第 5 墩 flow=♣，榜首 ♣3(75.2%) → "正在飞"尊重引擎，出 ♣3 ✓。

## 三十六、两条根因（v1.87 为何不够、三轮为何回退）

- **v1.87 的缺陷**：6NT 案中引擎榜首 ♦A（顶张兑现）与强制牌 ♦J（飞张）**同花色但语义相反**——"同花色即采信"等于用顶张替掉飞张，飞牌被吃掉。故 v1.93 加 rank 判据分流。
- **三轮回退的根因（B26 教训）**：**"桶内完胜比"在"不飞仍活"的世界里是假信号**。B26 案押对世界（西）里引擎榜首 ♦A 桶内做成率 0.542——不飞仍活，此时 "Q/A = 1.0/0.542 = 1.85" 看似完胜，实则全局期望 Q 47.4% < A 53.1%。而 6NT 案押对世界 A=0（不飞即死），桶内完胜才是真信号。**区分判据 = 押对世界榜首桶内值是否为零**——v1.96 三层判据即此分界的阈值化。
- **方法教训**：改判据前先在两个**同构反例**（6NT 要强制 / B26 要退让）上验证新判据方向相反，再动手。三轮试错均未做此预检。
