## 一、缘起：3NT 南庄牌局复盘暴露的问题链

同一副 3NT（南 2NT 开叫、北 3NT；南 ♥QJ♦765♣A32 / 北 ♠2♥2♦T32♣KJ4 残局阶段）连续暴露四类问题：

1. **多飞牌结构并存时启动顺序无依据**：探针同时报 ♦(Q) Δ0.51 与 ♣(Q) Δ0.80，系统按 dict 序处理，不按位置敏感度排序。
2. **流程被"滑动窗口新对象"复活**：第2墩曾启动飞 ♦(A)、东♦A 现身本应终结流程；但 A、K 出完后探针窗口只剩 Q，flow 被 Q 重建，此后每轮强制"非顶张方续飞 ♦5"，把 Δ0.8 的 ♣ 全程挤掉。
3. **探针引牌被"顶张方回手"规则卡死**：♣ 引牌是 ♣A（Δ最高），南持 ♣A 被判顶张方 → 要求先回手 → 无稳赢回手牌 → 整花色跳过 → 落到 Δ 更低的 ♦。
4. **伙伴侧结构的过手语义在 v1.72 合并中被删**：原 `_apply_lead_transfer` 的"队友侧探测到结构 → 过手给队友"逻辑，合池时未保留。

## 二、修改总览

| # | 机制 | 位置 | 说明 |

| 3 | 流程终结防复活（finesse_flow_ends） | `_apply_flow_continuation` / `_our_side_led_suit`；字段在 play_types.PlayState | 对象现身清 flow 时记 `finesse_flow_ends[s]=len(tricks)`；`_our_side_led_suit` 只统计终止点之后的领出——旧"曾领出"证据作废，须重新领出才有资格再次隐式启动（注：隐式启动与 `_our_side_led_suit` 已于 3.7 整体删除，`finesse_flow_ends` 保留作终结审计） |

## 三、关键决策与讨论记录（含走过的弯路）

### 3.1 多结构启动：合并→排序→逐个门控（用户定调）

用户原话要点：**"所有探测结果合池，按 Δ 从高到低排序后逐个过退让门控，启动第一个通过的花色——不是直接选最高的，最高的照样要过门控，不过就试次高的。"**

- 实现：`_apply_lead_finesse_check` 探测 `local(_detect_finesse_struct)` + `partner(_probe_partner_finesse_struct)` 合并；`_probe_lead_finesse_prefer` 按 Δ 降序试，每个花色过 `_finesse_launch_worthwhile` 四道闸。
- 边界：9砸后分支与进行中的 finesse_flow 仍排在窗口期启动之前（属于"已启动航线的优先规则"，不是"新启动选花色"）。

### 3.2 "假结构过滤"被否决（重要教训）

起初试图按"联手无高于对象的牌 → 假结构"加过滤，用户直接否决并被批评（"你太笨了，不配给我写程序"）：

- **位置性飞牌理解**："T 在 Q 的后面"（QT 结构飞 K）是真实位置性飞牌——飞张 = 对象紧邻下一档（K→Q、Q→J、J→T），只要飞张（+支撑）在联手，对象位置就翻转飞张赢墩，Δ>0.45 正是这类结构特征量级。**"无高于对象的牌即假结构"不可一刀切**（对象为 A 时天然无上方牌）。
- 结论：**不加假结构过滤**，只做用户要求的多结构 Δ 排序。假 Q 判据（A/K 均已出、无间张支点）已从记忆与文档删除。
- 复测佐证：同一位置 ♦(Q) 采样 Δ 仅 0.337（<0.4 阈值），属采样噪声摇摆；♣(Q) 小牌 Δ≈0.677、A Δ≈0.811，结构稳固。

### 3.3 流程终结：为什么用 finesse_flow_ends 而非"清理先行"

问题：对象 A 现身 → `del flow["♦"]` 正确触发，但**下一轮**隐式启动又用滑动窗口的新对象 Q 重建流程（`_our_side_led_suit` 历史领出恒真）。

候选方案对比：
- 方案A"清理先行 + 当轮防重建"：**否**。同轮重建被 `if s in state.finesse_flow: continue` 天然挡住（A 还在 flow 里时不会写 Q），该方案防的场景不存在；且只挡一轮，对跨轮复活无效。
- 方案B（采用，用户提出）：对象现身清 flow 时记录终结点，`_our_side_led_suit` 只统计终止点之后的领出——旧行为证据作废，须我方**重新领出该花色**（新证据）才有资格再次隐式启动。忠实"对象现身停、后续重新检测需新证据"。

### 3.4 窗口期引牌直出（用户提出）

探针选中的"引牌"（Δ 最大候选）同时指明了出牌方向与具体牌，窗口期启动应直接按引牌出：

- ♣ 对象Q Δ0.8 引牌♣A → 直接出 ♣A。
- **顶张方回手 / 非顶张方直飞是流程延续/9砸的规则，窗口期不适用**——之前把两套规则混用，导致"顶张方（持A）+ 无回手牌"时整花色被跳过，反而让 Δ 更低的 ♦ 起飞。
- 无引牌结构（αμ 模板等）仍走原有 combined 分流。

### 3.5 伙伴侧过手：恢复 v1.70 语义（删失教训）

v1.72 合并时删除了 `_apply_lead_transfer`，其"队友侧探测到结构 → 过手给队友引飞"的语义一起丢失，导致伙伴侧结构混入普通分流。恢复为专用分支：

- 伙伴侧结构 → 非9砸后、队友有该花色飞张小牌、`cash_reentry` 有稳赢回手牌 → 过手给队友，登记 flow 由队友引飞。
- 用户明确：**不再检测本侧顶张方**（原 v1.70 有"非顶张方 continue"前置，已删）。

**教训：重构合并函数时，必须逐条核对被删函数的语义是否仍有落点，不能只关注排序/门控等显性行为。**

### 3.6 探针口径确认

- 每花色**所有可出牌**均做东/西分桶检测；最终只保留 Δ 最高的一张作代表（引牌）。
- ♣2 与 ♣3 的 Δ 相同（0.677）——同策略低引，赢墩期望一致。
- 引牌目前既用于展示（`说明`），也作为窗口期直出的实际出牌依据（2026-09-11 起）。

### 3.7 隐式启动无存在价值，整体删除（2026-09-11）

用户复盘 6♠ 例时发现 `finesse_flow[♠] = A` 的来源是**隐式启动**：历史上我方曾领出 `♠`，某墩探针偶发报到 ♠(A) 结构，即被补登进 flow（`_our_side_led_suit` 判定"曾领出"恒真）。该路径**条件过宽、不走退让门控、且无任何日志**。

用户追问链：隐式启动目的 → 补登记是否以检测到结构为前提 → 现在还有用吗 → 定调"删掉"。

- **删除**：`_apply_flow_continuation` 不再含"曾领出 + 对象未现身 → 补登"分支，配套 `_our_side_led_suit` 方法一并移除（`_finesse_obj_played` 后仍记 `finesse_flow_ends`，改作终结审计）。
- **飞牌流程登记仅显式路径**：窗口期启动改出 / 引牌直出 / 伙伴侧过手 / 引擎已在该花色的补登记，四类入口均经过退让门控且带日志。
- **教训**：凡"隐式补登"类机制——基于历史行为证据替代当墩结构判定的——都要警惕其是否绕过门控/无日志。流程登记应只从显式决策出发。

## 四、经验教训

1. **不做自认为合理的扩展**：用户要求"只加排序"就只做排序；真假结构过滤先讲清规则、确认后动手，确认选项必须忠实用户原话。
2. **窗口期启动 ≠ 流程延续/9砸**：引牌直出 vs 顶张方回手/续飞是两套语义，分属不同阶段，不可互相套用。
3. **流程终结要防"滑动窗口复活"**：对象现身是硬终点；后续重新启动须有新的行为证据（重新领出该花色），不能靠滑动窗口的新对象自动复活。
4. **删除函数 = 删除语义**：v1.72 合池删除 `_apply_lead_transfer` 丢失"伙伴侧过手"，当日即回补。重构时先列被删函数的行为清单。
5. **探针 Δ 是采样量**：同一位置 ♦Q Δ 0.46/0.51/0.337 随采样波动，压在阈值线（0.4）附近的结构不可靠；判定结构要综合 Δ 稳定性而非单次采样。
